# Scriare — Architecture Plan (MVP)

## Philosophy
"Build stories, not syntax." Writing-first workspace for branching narrative. Not a game engine. Closest comparison: a document editor + lightweight Twine-style branching + instant playtesting. Branching is written, not drawn: choices and their text are authored as Choice Blocks directly inside the document; the graph only ever visualizes and lets you navigate/organize what's already written, and stays non-destructive (no drawing/editing connections, no deleting scenes from the graph). Play Mode lets you experience that branching story instantly inside the app — no export step, no second window — and is strictly read-only: it can never modify the story, it's guaranteed to *read* the same way the story was written (same column width, same typography, since v0.6.2), and as of v0.7.0 it plays back every block in the exact order it was written, not just the prose. As of v0.4.0 the explicit design north star is "feel closer to Notion or Word than to a technical editor" — and v0.7.0 restates that explicitly as a hard constraint: Scriare stays a rich text editor with narrative elements embedded inside the document, never a Notion-style block/card editor. As of v0.5.0 the project also has a long-term organizational backbone: the Content Browser, built generically from day one so future content types (Characters, Locations, Notes, Assets) can plug in without a redesign. As of v0.6.0 the Content Browser also behaves like a real desktop file explorer (multi-select, multi-drag, bulk actions, custom dialogs instead of native OS popups). As of v0.8.0 the Play runtime is also explicitly treated as its own product surface, not just a preview — a dedicated Start Scene, a proper ending screen, Escape-to-exit, and a scene fade, all built on a runtime layer structurally separate from the editor's own UI components. As of v0.9.0 the app also has a deliberate visual identity — a premium, switchable theme system — layered on top without touching any of the above; this milestone changed only how the app looks, never how it behaves. As of v0.10.0 the Story Graph's *interaction quality* got a dedicated pass — drag/hover/selection/zoom feedback — without changing what the graph can do or how it looks at rest. As of v0.11.0 the app's own layout became fully dockable — every side/bottom panel (Content, Scene Details, the Story Graph) can be collapsed independently, so a writer can go down to just the page when that's all they want; v0.11.1 polished that further so all three panels behave and look the same way when docking, and v0.11.2 finished that consistency pass by making the two sidebars' collapsed-strip labels match the app's usual bold/uppercase section-header styling instead of plain sentence case. As of v0.12.0, the flagged "theme/font exploration" ask (see v0.11.0) arrived and went the opposite direction from more colour: the app's four colourful themes were replaced outright with a strictly minimal black/white/gray system (Dark default, Light), the app's own UI chrome moved from Manrope to Inter, and colour itself was narrowed to a deliberate exception — reserved for genuinely destructive or constructive actions, not decoration — while the rich text editor and Play Mode's own typography were explicitly left untouched. v0.12.1 tuned that palette once more: Light mode's background/surface/border tiers moved a uniform notch off pure white, since near-white read as too stark, while Dark mode and every contrast step between tiers stayed exactly as they were. As of v0.13.0, the brand mark itself became a real logo asset — the project owner's finished circular badge artwork (from `other_materials/logos`) replaced the typographic blackletter "S" wherever the logo renders in-app, swapping between its Dark/Light variants to match the active theme, and the OS-facing app/taskbar icon was regenerated from that same artwork's dedicated Icon variant. As of v0.14.0, the Story Graph — feature-complete since v0.10.6 — went through an explicit evaluation-and-polish sprint rather than a features sprint: every interaction category (dragging, lift, edges, frames, selection, hover, zoom, pan, cursor) was inspected against what already existed, and only the categories that felt incomplete (frame lift/hover/selection parity with scenes, edge selection feedback, a cursor-inheritance bug) were changed — everything already production-ready was left alone. v0.14.1 followed up on a real-world usability report about that same graph area — Frames specifically — rather than opening a new evaluation pass: both a sizing problem (frames too small, by default and by resize floor, to actually hold a cluster of scenes) and a rendering problem (choice lines connecting scenes inside a frame could loop back on themselves) were investigated and fixed, without touching anything else v0.14.0 had just settled. v0.14.2 fixed the actual reason Frame resizing looked broken to begin with: the v0.14.1 sizing fix was correct, but Frames could never be selected in the first place, because Frame selection had never been wired into this app's own state the way every other per-node status here is — clicking a Frame briefly registered internally and was silently un-set on the very next redraw. v0.15.0 was a second explicit "evaluate before changing" sprint on the Story Graph — this time covering navigation (pan/select), Frame resizing's live feedback, and scene-selection-vs-Scene-Editor-focus — and it generalized the v0.14.2 Frame-selection fix into a single mechanism covering every node and true multi-selection, rather than treating Frame selection as its own special case. v0.15.1 was a rapid bugfix follow-up on that same generalized mechanism: three issues reported immediately after v0.15.0 shipped — a multi-selection only moving the one node the pointer grabbed, a persistent selection-bounding-box the request never asked for, and a Frame-resize animation that only felt natural from the bottom-right handle — all traced to gaps in how thoroughly the v0.15.0 generalization had been carried through, not to new problems of their own. v0.16.0 finally picked up the one item v0.15.1 deliberately deferred: Auto Layout previously ignored any scene grouped into a Frame, which meant a project relying on Frames for organization got a visibly broken Auto Layout the moment it was used — Frames now participate in Auto Layout as first-class layout nodes, sized to their own footprint, while every scene's arrangement *inside* its Frame is preserved exactly as the writer left it. As of v0.17.0, the Story Graph went through a third dedicated interaction-feel pass (Sprint 8B) — not a features sprint, not a redesign, but an explicit "evaluate before changing" polish pass over cursor states, drag feel, hover/selection feedback, navigation feel, edge behaviour, auto-scroll, and cross-interaction consistency, so the graph feels comparable to professional creative software without functionally feeling any different. As of v0.18.0, the evaluation lens widened for the first time from the Story Graph specifically to the application as a whole (Sprint 8C): with the graph's interaction model settled across three dedicated passes, this sprint asked whether Scriare *presents itself* as a finished, native desktop product — window/taskbar/menu-level OS identity, cross-panel spacing/typography consistency, and a handful of remaining hardcoded-colour/naming inconsistencies the graph-focused sprints had no reason to touch — again strictly evaluate-and-polish, not a redesign, and again preserving every existing workflow untouched. As of v0.19.0, the evaluation lens widened once more — from the desktop shell specifically (Sprint 8C) to every existing feature in the application (Sprint 8D), the final pass of the Sprint 8 arc: every named system (editor, toolbar, Choice Block, Content Browser, Story Graph, Inspector, Project Settings, Play Mode, dialogs, popups, context menus, keyboard shortcuts, drag & drop, folder/scene management, Start Scene) was evaluated against a production-quality bar, with the explicit instruction to leave anything already production-ready untouched rather than polish for polishing's sake — of sixteen systems evaluated, fifteen needed no change at all, and the one genuine gap found (`NewProjectDialog.tsx`, the sole dialog never migrated onto the shared `<Modal/>` shell) was fixed to match its siblings.

## Versioning convention
Starting from the writing-experience milestone (**v0.0.2**), every delivered build gets a proper version number in `package.json`. Bump size depends on the scope of the update:
- Patch (0.0.x): small fixes or tweaks to existing features.
- Minor (0.x.0): a new milestone/feature set (e.g. branching, graph navigation, Play Mode, the writing-workflow redesign, the Content Browser, the desktop UX polish sprint, Narrative Blocks, the premium theme system, the graph interaction polish sprint, the dockable-layout sprint, the Minimal redesign, the Real Logo swap, the graph interaction evaluation-and-polish sprint, Frames joining Auto Layout).
- Major (x.0.0): reserved for once the app is a complete, stable product (post-MVP).

Every update is delivered as the **full runnable project as a zip** (not partial/diff files), so it can be unzipped and run immediately with `npm install && npm run dev`. **Zip format:** the zip file is named `v<version>.zip` (e.g. `v0.7.0.zip`) and its single top-level folder inside is named only `v<version>/` — the project files sit directly inside that folder, with no extra nested `scriare/` subfolder. Every delivery is verified by extracting that exact zip fresh into a clean scratch folder, running `npm install` and a production build there, before sending it. **Every delivery is also accompanied by a one/two-sentence briefing of what's new in that version** — a standing user request, not a one-off. As of v0.9.0, delivery instead happens by syncing files directly into the user's connected local folder via the device bridge rather than a zip — the same standing rules (type-check + production build verified before sending, briefing included) still apply.

## Known pitfalls
**Never run `tsc -b` on this project.** Build-mode `tsc -b` emits compiled `.js`/`.jsx`/`.d.ts` files directly next to their TypeScript sources in `src/`. Because Vite's module resolution checks `.jsx` before `.tsx`, a leftover `.jsx` file silently shadows the real source — edits to the `.tsx` file stop having any effect on the running app with no error at all. This happened during v0.1.0 development and was caught only by grepping the built bundle for expected strings. Always type-check with `npx tsc --noEmit -p tsconfig.node.json` / `-p tsconfig.web.json` instead, and if `tsc -b` is ever run by mistake, delete every `.js`/`.jsx`/`.d.ts` it created under `src/` (except the two hand-written `src/preload/index.d.ts` and `src/renderer/src/env.d.ts`) before doing anything else.

**Custom React Flow node types need their own `<Handle>` elements.** Unlike React Flow's built-in default node (which has a target handle on top and a source handle on bottom automatically), a custom node component (`SceneNode`, `FrameNode`) renders none of that for you — omit it and edges have nowhere to attach, so they silently don't render at all, with no console error. This broke in v0.2.0 when scenes moved to a custom node type, and was fixed in v0.2.1 by giving `SceneNode` exactly one invisible target handle and one invisible source handle — matching what the default node already did. Keep it to one handle of each type unless every edge is updated to specify `sourceHandle`/`targetHandle` explicitly (multiple same-type handles are ambiguous otherwise).

**A custom node's handle sides must match the auto-layout direction.** `SceneNode` originally put its handles on Top (target) and Bottom (source), which matched React Flow's own default node — but Auto Layout arranges scenes in a left-to-right flow (`computeAutoLayout` uses dagre's `rankdir: "LR"`). With vertical handles, every edge had to loop out the bottom of one box and back into the top of the next box placed to its right, which bent awkwardly and crossed other edges after running Auto Layout. Fixed in v0.6.1 by moving `SceneNode`'s handles to Left (target) / Right (source), matching the flow direction. If the layout direction ever changes again, the handle sides need to change with it.

**A fixed-side handle plus an axis-constrained edge type only looks right for connections that flow the way the handles assume — anything else forces the edge into a hard, ugly loop.** `SceneNode`'s handles are fixed to Right (source) / Left (target), tuned for Auto Layout's left-to-right ordering, where a target is always somewhere to the right of its source. That assumption holds for every Auto Layout-produced connection, but not for a scene the writer drags freely — which happens constantly once Frames became a practical way to group a cluster of scenes together (v0.14.1) — where a connected scene can just as easily end up behind, above, or below the one it links to. `smoothstep` (used since v0.2.0) can only route in straight, axis-aligned segments, so a "backward" connection like that has no straight path available and gets forced into a step-out/double-back/step-in loop — cosmetically fine as an edge case when it was rare, but common and glaring once tight, non-linear scene clusters inside Frames became a normal way to work. Fixed in v0.14.1 by switching edges to `type: "default"` (bezier), which curves smoothly toward its target from any relative direction using the same fixed handles — no loop, regardless of which way the connection actually points. The general rule: an edge type that can only draw straight/axis-aligned paths (`smoothstep`, `step`) is only a safe choice when every connection is guaranteed to flow the direction the handles were tuned for; the moment nodes can be arranged freely instead of by a fixed layout algorithm, a curve-based edge type (`default`/bezier, `simplebezier`) is the one that degrades gracefully instead of visibly breaking.

**The editor and Play Mode must share one reading-column definition, not two copies.** Both render the same story content (one live via ProseMirror, one as static HTML from `generateHTML()`), and both need to look the same width and typography — but until v0.6.2 each component kept its own copy of the "centered, capped-width, prose-typography" wrapper classes, which is exactly the kind of duplication that quietly drifts apart. `utils/readingColumn.ts` now holds the single definition (`READING_COLUMN_CLASS`, `READING_PROSE_CLASS`) that both `SceneEditor.tsx` and the Play runtime import — any future change to the reading experience's width or typography should happen there, once, not in each consumer. As of v0.12.0, this same shared definition is also what made it straightforward to explicitly exempt the reading column from an app-wide typography change — see the font-pin pitfall below.

**A styled block should be styled once, by selector, not by two separate renderers agreeing to duplicate CSS.** `Callout` (v0.7.0) is deliberately a plain Tiptap node with no custom NodeView and no per-renderer styling code — its entire look (background tint, accent border, icon) is one CSS block in `styles/index.css` targeting `[data-type="callout"]`. That selector matches the node's DOM wherever it renders, live inside the ProseMirror editor or inside the Play runtime's static `generateHTML()` output, so the two can't visually drift apart the way width/typography once did (see the reading-column pitfall above) — there's only one place the styling is defined at all. As of v0.9.0 this same one-selector principle backs the entire colour system: every theme is a block of CSS custom properties, so a component never hardcodes a colour.

**`*.tsbuildinfo` files must never end up in a delivered zip.** `.gitignore` already excludes them, but the packaging step (a plain `tar`/zip of the project folder) doesn't consult `.gitignore` — it has to explicitly exclude `*.tsbuildinfo` itself, or stray incremental-build files from a previous `tsc --noEmit` run get bundled in (this happened silently in the v0.7.0 and earlier zips before being caught and fixed during v0.8.0 packaging). Always exclude them explicitly when assembling the zip, and spot-check `unzip -l` for anything that isn't source/config before sending.

**A single-source-of-truth field beats a mirrored flag whenever "exactly one" is a requirement.** v0.8.1 added two more places to set the Start Scene (a Content Browser context menu item, an Inspector checkbox) alongside v0.8.0's Project Settings dialog. All three call the same `projectStore.setStartScene(sceneId | null)`, which writes straight into the single `project.startSceneId` field — there was never a temptation to add a per-scene `isStart` boolean that all three UIs would need to keep in sync (and could drift out of sync, exactly like the reading-column and Callout-styling pitfalls above). Any future "exactly one of these" requirement should default to this pattern first.

**Never call `preventDefault()` in a `mousedown` handler on an element nested inside a `draggable` ancestor.** v0.6.1 added `onMouseDown={(e) => e.preventDefault()}` to `ContentTreeRow.tsx`'s inner `<button>`s (the folder-expand arrow and the scene/folder name label) to suppress a stray focus/text-selection highlight during Shift+Click. That silently broke native HTML5 drag & drop for the entire row: Chromium uses `mousedown` to begin recognizing a drag gesture, and calling `preventDefault()` there — worse, on a `<button>`, which has its own default mousedown behavior competing with the ancestor's `draggable` — stops `dragstart` from ever firing. Click-based interactions (plain click, Ctrl+click, Shift+click, right-click) all kept working because none of them depend on `dragstart`, which is exactly why the bug went unnoticed through v0.6.1–v0.8.2 despite a full regression audit in v0.8.2 (that audit read the reducer logic and confirmed it was correct, but never exercised an actual drag gesture in a browser — a static code read cannot catch a browser-event-timing bug like this one). Fixed in v0.8.3 by making those two elements plain `<div role="button" tabIndex={0}>`s instead of `<button>`s, with the `mousedown` handler removed entirely — the row's existing `select-none` class and each element's `focus:outline-none` already suppress the highlight without touching `mousedown`. Going forward: never call `preventDefault()` on `mousedown` for anything living inside a `draggable` container, and prefer non-form-control elements (`div`/`span` with `role="button"`) over real `<button>`/`<a>`/`<input>` for a draggable row's inner controls, since those have their own default drag-related behavior that can conflict with the ancestor's. Any fix for a "stray highlight/outline" class of bug should be verified with an actual drag test, not just a visual check — this is now a standing exception to "a clean build/tsc doesn't prove a feature is wired up," since this bug produced a perfectly clean build and complete UI.

**A scratch file dropped into the project root during work-in-progress editing will get packaged if it isn't cleaned up before zipping.** During the v0.8.2 regression audit, a local copy of an in-progress architecture-doc draft (`arch_v0.8.1.md`) was briefly copied into the project's root directory as part of composing that update, then left there when the update actually succeeded — the next packaging pass picked it up and it ended up in the pre-verification zip (caught by the pre-send `unzip -l` file-count check, which is exactly why that check exists). Any file written for the purpose of composing a Project-doc update belongs in a scratch location outside the repo, never inside `scriare/` itself, even briefly.

**A CSS `@import` must be the first rule in its file — including transitively.** Adding `@import "./themes.css"` after the `@tailwind` directives in `index.css` (v0.9.0) produced a build-time warning (`@import must precede all other statements`) and would have silently failed to load in some environments, because the Google Fonts `@import` sitting near the *bottom* of `themes.css` was itself preceded by that file's own theme-variable rule blocks. Fixed by moving `@import "./themes.css"` to the very first line of `index.css` (before any `@tailwind` line) and moving the Google Fonts `@import` to the first line of `themes.css` (before any `:root`/`[data-theme]` block). Any CSS file that both defines rules and pulls in an external stylesheet needs its `@import` line(s) first, full stop — this applies per-file, not just to the entry stylesheet.

**A CSS `transition` on a value React Flow updates every animation frame will fight the drag instead of helping it.** Sprint 8A (v0.10.0) needed dragged nodes to feel smooth, but React Flow already repositions a dragging node via an inline `transform` on every pointer-move — adding a CSS `transition: transform` unscoped would add lag between the cursor and the node during an actual drag. Fixed by scoping the rule to `.react-flow__node:not(.dragging)`, so a *programmatic* position change (Auto Layout, a frame settling after drag-stop) eases in, while a live drag still tracks the cursor with zero added latency. The same reasoning applies to edge paths: their `d` attribute must never be transitioned (it changes every frame right along with node position), only cosmetic properties like `stroke`/`stroke-width`/`opacity`. **This same rule extends to any other incremental, cursor-driven interaction, not just plain dragging** — see the resize-transition pitfall below (v0.15.1), where the same class of bug showed up in `NodeResizer` because resizing was never included in the `:not(.dragging)` exclusion to begin with.

**Never feed drag-hover state through React Flow's controlled `nodes` prop — it silently breaks the drag it's decorating.** v0.10.0's first cut of the Frame drop-target highlight stored `{sceneId, hoverFrameId}` in React state and flowed it into `FlowPanel`'s `nodes`/`edges` memo as an `isDropTarget`/`isDragging` data flag, same as every other per-node visual (`isActive`, `isStart`). That broke scene dragging outright: React Flow only keeps tracking a node's live drag position when the node object it receives via the controlled `nodes` prop is *reference-identical* to the one it already holds internally (`adoptUserNodes` in `@xyflow/system`, called from `StoreUpdater`'s effect on every `nodes` reference change) — any other object makes it recompute that node's rendered position fresh from the incoming `position` field, which during a drag is still the stale, not-yet-committed store value. Fixed in v0.10.1 by moving the Frame drop-target highlight to a plain CSS class toggled directly on the DOM (`scriare-drop-target`, added/removed via `querySelector('.react-flow__node[data-id="..."]')`, tracked in a ref rather than state). This is correct and stayed correct — but v0.10.1 also (mistakenly) removed the *only* thing that had been forcing a re-render during a scene drag at all, which uncovered a second, deeper bug — see the next entry, which supersedes the "restores the exact reactivity scene dragging had before v0.10.0" framing this entry originally shipped with: that pre-v0.10.0 reactivity was itself never sufficient for scene drags specifically (only for frame drags), it had simply never been exercised carefully enough to notice.

**This app never wires up React Flow's `onNodesChange` — which means NOTHING makes a node visually track the cursor during a drag except your own code explicitly forcing a re-render with the node's live position, every single pointer-move.** This is the actual, complete root cause behind the "dragging doesn't move the node" reports across v0.10.0 and v0.10.1, and it predates Sprint 8A entirely. React Flow's rendered node position comes from `internals.positionAbsolute` inside its internal zustand store; a node's low-level drag handler (`XYDrag` in `@xyflow/system`) does update that value on every pointer-move, but `triggerNodeChanges()` — the function that would normally notify the store's subscribers of the change — only does anything when either `hasDefaultNodes` (uncontrolled mode, not used here) or an `onNodesChange` prop is present. Neither is true in this app, so that internal update is invisible to React: nothing re-renders, and the node's DOM transform is stuck at whatever it was computed to be when the drag started. Frame dragging has always visually worked *despite* this, not because of some different internal mechanism, but because `FlowPanel.handleNodeDrag`'s frame branch calls `setFrameDrag(...)` **unconditionally on every single pointer-move** (never gated on "did anything meaningful change" — only on "is this still the frame being dragged"), which is a genuine React state update that forces `FlowPanel` to re-render, recompute the `nodes` array with the frame's current cursor-driven position baked in, and hand that fresh array to `<ReactFlow>` — which *does* trigger a real store update via `adoptUserNodes`. Scene dragging in both v0.10.0 (whose scene-drag state update was gated behind "did the hovered frame change," so it fired at most a few times per drag, not every frame) and v0.10.1 (which removed React state from the scene-drag path entirely, going pure-ref/DOM) never had this unconditional per-frame state update, so a dragged scene visually never moved at all until drop — "sits in place while you drag your mouse with nothing," reported identically both times. Fixed in v0.10.2 by adding a `sceneDrag: {sceneId, origin, dx, dy}` state, updated completely unconditionally in `handleNodeDrag`'s scene branch (mirroring `frameDrag` exactly, not gated on the frame-highlight check, which stays a separate, still-DOM-driven concern), and fed into the dragged scene's position in the `nodes` memo the same way `frameDrag` already feeds a dragged frame's position. **The general rule going forward:** in this codebase, specifically because `onNodesChange` is not wired up, any node type that needs to visually move during an active drag (not just settle correctly on drop) needs its own live offset state updated unconditionally on every `onNodeDrag` call — a cosmetic, DOM-only side effect (like the frame-hover highlight) is fine to keep off the React state path, but the position itself is not optional to feed through state. If a future node type is added that needs to be draggable, give it the same `{id, origin, dx, dy}` pattern from day one rather than assuming React Flow's own drag tracking will "just work" visually — in this app, it structurally can't, without `onNodesChange`. **v0.15.1 sharpened this rule once more: the live-offset pattern has to key off every node actually being dragged, not just the one node React Flow reports as "grabbed."** `frameDrag`/`sceneDrag` originally stored a single `{frameId/sceneId, origin, dx, dy}`, correct only for a lone dragged node — but `onNodeDrag`/`onNodeDragStart`/`onNodeDragStop` all receive a *third* argument, `nodes: Node[]`, listing every node actually moving together (the whole multi-selection, when more than one node is selected). Reading only the second argument (`node`) meant a multi-selected drag correctly showed every selected node highlighted (selection is tracked separately, see the `selectedGraphIds` pitfall above) but only the grabbed node's position ever got a live offset — the rest of the group visually stayed in place. Fixed by generalizing `frameDrag`/`sceneDrag` from a single offset into `Map<nodeId, DragOffset>`, built and updated from the `nodes` array each handler already receives, so every dragged node — not just the grabbed one — gets its own live offset fed into the `nodes` memo.

**Making a dragged node's position update on every pointer-move (the fix above) turns any other, unrelated per-node computation living in the same memo into a per-pointer-move cost too — profile what's inside a memo before making it re-run every drag frame.** v0.10.2's `sceneDrag` fix made `FlowPanel`'s combined `nodes`/`edges` memo recompute on every pointer-move of a scene drag, same as it always did for frame drags. That memo was also calling `extractChoices()` — a full walk of a scene's Tiptap document — for *every* scene in the project, twice over (once for each scene's `choiceCount` badge, once more to build every edge), on every single recompute. Frame dragging had silently paid this cost since v0.2.0 without complaint (frame drags are rarer and shorter); scene dragging paying it for the first time in v0.10.2, at mouse-move frequency, was enough synchronous main-thread work on a project with a non-trivial scene count to stall Chromium's renderer hard enough that it stopped painting the graph entirely — recoverable only by reopening the project. Fixed in v0.10.3 by splitting `FlowPanel`'s single memo into a `choiceCountByScene` map + `edges` array memoized on `project` alone (so `extractChoices()` only reruns when a scene's content actually changes) and a separate `nodes` memo that depends on `frameDrag`/`sceneDrag` but does nothing more expensive than position arithmetic and map lookups. The general rule: before making any state update fire on every pointer-move of a drag (the previous entry's fix), check everything already living in the memo that state feeds — a live position needs to update every frame, but content-derived data usually doesn't, and bundling the two in one memo makes the cheap thing pay the expensive thing's cost on every frame.

**A controlled `nodes` prop that never carries a `measured` size will randomly "forget" it mid-drag, once the node object is rebuilt on every pointer-move.** After v0.10.3 fixed the graph-goes-blank stall, dragging could still freeze at random after 1-2 seconds — the node stopped tracking the cursor while the mouse button was still held, with no consistent trigger (fast or slow movement, different areas of the graph). Per an explicit request to debug rather than guess, the drag implementation was traced through `@xyflow/react`/`@xyflow/system`'s own source before any fix was attempted, and instrumented with temporary, purely-observational logging (console timestamps, a `requestAnimationFrame` DOM poll of the dragged node's actual computed style/bounding rect, window-level `pointerup`/`pointercancel`/`blur` listeners) to gather live evidence. The user's own console log then showed React Flow's `error015` ("trying to drag a node that is not initialized... use onNodesChange") firing hundreds of times per drag, confirming the leading hypothesis: `@xyflow/system`'s `adoptUserNodes` only carries a node's already-measured `measured: {width, height}` forward when the incoming node object is *reference-identical* to the one it already has internally — and because this app's `nodes` memo builds a brand-new object literal for every node on every drag-frame recompute (required for the v0.10.2 live-cursor-tracking fix), and those objects never carried a `measured` field at all, `adoptUserNodes` reset every dragged node's `measured` size to `{width: undefined, height: undefined}` on every single pointer-move. That flips the node's `hasDimensions` check to false, which hides it (`visibility: hidden`) and re-triggers its `ResizeObserver` unobserve/observe cycle — a measure/reset race that could lose outright under load, leaving the node stuck unmeasured (and therefore visually frozen) until something else forced a full remeasure, matching "reopening the document fixes it" and the reported inconsistency (frame-timing dependent). Fixed in v0.10.4 by wiring up `onNodesChange` for the first time in this app's history — not to manage node state through it (this app still manages position via `frameDrag`/`sceneDrag`, per the pattern above), only to capture React Flow's own `dimensions`-type change events into a ref-keyed cache (`measuredSizeRef`), and feeding that cached size back in as each node's `measured` field so it survives being rebuilt as a new object every drag frame. **The general rule going forward:** any node object this app constructs for the controlled `nodes` prop needs to carry forward whatever measured/internal state React Flow itself reported for that node (via `onNodesChange`), not just the app's own `id`/`type`/`position`/`data` fields — rebuilding a node from scratch every frame is fine for state this app owns (position), but silently drops state only React Flow owns (measured size) unless that state is explicitly captured and re-supplied.

**Caching a value in a plain `ref` doesn't make anything re-render — if a downstream consumer needs to see that value change, something has to explicitly force a recompute. And that "something" has to be wired all the way through, not just introduced — a `useState` bump that isn't listed in the consuming `useMemo`'s own dependency array does nothing at all.** v0.10.4's `measuredSizeRef` fix correctly preserved each node's measured size across drag-frame recomputes, but writing into a ref is invisible to React by design — updating it doesn't make `FlowPanel` re-render, so on a freshly opened graph, a node's real size (known as soon as React Flow's `ResizeObserver` reports it, shortly after mount) only reached the `nodes` memo the *next* time something else happened to force that memo to recompute — in practice, the first time any node was dragged. Before that, the main graph canvas still looked correct (it measures each node independently, straight off the DOM, regardless of what's in the controlled `nodes` prop), but the MiniMap — which colours/sizes each node from the object *this app* hands it — kept drawing every node as an unmeasured, colourless box until a drag happened to trigger a recompute. v0.10.5's first attempt at a fix added a `useState` counter bumped whenever a cached size actually changed, on the (correct) theory that a state update would force a re-render — but a re-render alone doesn't make `useMemo` recompute: `useMemo` only reruns when something in *its own* dependency array changes, and that counter was never added to the `nodes` memo's array, so the re-render happened but `nodes` kept handing back its stale, memoized value. The bug therefore looked identical after v0.10.5 as before it, both on first launch and — a second symptom reported at the same time — after collapsing and reopening the Flow panel, which fully unmounts `<ReactFlow>` and restarts measurement from scratch each time, hitting the exact same missing-dependency gap. Actually fixed in v0.10.6 by adding that counter (renamed `measuredVersion` for clarity) to the `nodes` memo's dependency array itself, so a size-cache change now genuinely forces the array — and therefore the MiniMap — to refresh immediately, with no drag required, whether on first launch or after any number of panel collapse/reopen cycles. The general rule: a ref is fine for a cache another render already in flight will read, but the moment something needs to react to that cache being populated or changing (not just read it opportunistically), pair the ref with a state update gated on "did this actually change" *and* confirm that state is actually listed in every `useMemo`/`useEffect` dependency array meant to react to it — a state bump that reaches nothing costs nothing and fixes nothing, and looks, from a clean build alone, exactly like a working fix.

**A panel's own header wrapping just its label in a `<button>` leaves the rest of a thin collapsed bar dead space.** v0.11.0 gave the Content panel the same collapsed/expanded structure Scene Details already had, but the Story Graph's own collapse toggle (present since v0.10.0) only ever wrapped its "Flow" label text in a `<button>`, not the full header row — so once collapsed to its 36px strip, only the label itself was clickable to re-expand it, while the sidebars' collapsed strips were always a single full-size `<button>` (the whole thin rail is the click target). Reported directly as an inconsistency once all three panels were dockable side by side. Fixed in v0.11.1 by branching `FlowPanel`'s collapsed render into its own full-width `<button>` (mirroring the sidebars) instead of a `<div>` header containing a small internal toggle button. The general rule for any future dockable panel: a collapsed rail should always BE the click target, not contain one.

**A collapsed panel's label needs the same typography treatment as the rest of the app's section headers, not whatever the element's default styling happens to be.** When v0.11.0 gave `ContentBrowser.tsx` its own collapsed vertical strip (mirroring `InspectorPanel.tsx`'s pre-existing one), both copied `text-xs tracking-wide` for the label but neither added `font-semibold uppercase` — the two classes every other section header in the app (Content's and Scene Details' own expanded headers, the Story Graph's collapsed/expanded labels) already carries. The two collapsed strips were internally consistent with each other (identical classes on both), but visually out of step with the rest of the app's small-caps section-header convention, which read as "the font looks different when docked" once noticed. Fixed in v0.11.2 by adding `font-semibold uppercase` to both. The general rule: a new instance of a recurring UI pattern (a section-header label, here) should copy every class that pattern's existing instances share, not just the ones that happen to visually resemble it at a glance.

**An app-wide font change silently reaches content that was never meant to change, unless that content already had its own shared definition to pin.** v0.12.0's Minimal redesign switched the app's `body` font-family from Manrope to Inter, per an explicit instruction not to touch the rich text editor's own typography. Because the reading column (`utils/readingColumn.ts`'s `READING_PROSE_CLASS`, used by both `SceneEditor.tsx` and Play Mode) never set its own font-family — it simply inherited whatever `body` had — changing `body`'s font would have silently changed the story's on-screen typography too, exactly the thing the request said not to touch, with nothing in a diff or a build flagging it as a problem. Fixed by adding a `.font-reading` class (pinned to the old Manrope stack) to `READING_PROSE_CLASS` itself, so the reading column keeps its typography explicitly rather than by accident of not having changed yet. The general rule: before changing an app-wide default (a font, in this case; a colour or spacing scale would be the same story), check whether anything that's supposed to be exempt was relying on inheritance rather than an explicit value — inheritance-based "consistency" silently breaks the moment the thing above it changes.

**A palette-tier tweak should shift a uniform amount across every affected tier, not just the one variable someone actually complained about.** When Light mode's background was reported as reading too close to pure white (v0.12.1), the fix moved `--bg`, `--surface`, `--surface-2`, `--surface-3`, `--border`, `--border-soft`, and `--border-faint` (plus the translucent variants derived from `--surface`/`--surface-2`) down by the same 4-point lightness step, rather than lowering `--bg` alone. Shifting only `--bg` would have closed (or inverted) the gap between it and `--surface` — the exact same "one variable changes, its neighbors don't, and the relationship between them silently breaks" failure mode as the font-inheritance pitfall above, just applied to a numeric scale instead of a CSS property. The general rule: a value that exists only to sit at a fixed *distance* from its neighbors (a tier in an elevation scale, a step in a type ramp) should be edited by shifting the whole scale, never by moving one tier and hoping the others still make sense next to it.

**A CSS rule inherited from a draggable ancestor bleeds into interactive children unless explicitly overridden — even ones that already stop the drag from starting.** `.react-flow__node { cursor: grab; }` (v0.10.0) is meant to signal "this whole box is draggable," but `cursor` is an inherited CSS property, so `FrameNode.tsx`'s title `<input>` and delete `<button>` — both of which already call `stopPropagation()` on `mousedown` to prevent an actual node drag from starting — still visually showed a grab-hand cursor while hovered, even though hovering them doesn't drag anything. Stopping the drag *behavior* on an element does nothing to its inherited *cursor value*; those are two independent things a nested interactive element needs to handle separately. Fixed in v0.14.0 by giving the input `cursor-text` and the button `cursor-pointer` explicitly. The general rule: any interactive element nested inside a `cursor: grab`/`cursor: pointer` ancestor needs its own explicit `cursor` value, regardless of whether its drag/click behavior is already correctly isolated from the ancestor's.

**A resizable container's default size and resize floor both need to reflect what it's actually meant to hold, not just "small enough to not be intrusive."** `Frame`'s original default size (360×260, v0.2.0) and resize-down floor (`FRAME_MIN_WIDTH`/`FRAME_MIN_HEIGHT`, 200×140) were both sized conservatively, without reference to `SCENE_NODE_WIDTH`/`SCENE_NODE_HEIGHT` (180×56) — the thing a Frame actually exists to hold multiple of. The result, reported directly (v0.14.1): a brand-new Frame could comfortably fit only one or two scene cards before feeling cramped, and resizing one down (NodeResizer was already fully wired up and working — this wasn't a resize-mechanism bug) could shrink it well past the point of holding even one card usefully. Fixed by raising both numbers with the scene card's own dimensions in mind: the default grew to 480×320 (room for a small cluster right away) and the floor to 260×170 (still comfortably fits at least one card at the smallest a Frame can go). The general rule: any size constant for a container meant to hold N of another sized thing should be derived from — or at least sanity-checked against — that other thing's own dimensions, not picked independently.

**A per-node status driven by a graph library's own internal state needs that state fed back through the same controlled-prop channel every other per-node status in this app already goes through — otherwise it silently resets on the very next redraw.** v0.14.0 gave a selected Frame an accent border and made `NodeResizer`'s handles visible only `isVisible={selected}`, both reading React Flow's own built-in `selected` flag on the node — the one piece of per-node state in this whole app that was never routed through this app's own controlled `nodes` array. Every other per-node status here (`isActive`, `isStart`, drag offsets, measured size) is explicitly computed and fed into the `nodes` memo on every recompute, precisely because this app's `nodes` memo already rebuilds a fresh object for every node very frequently (every drag frame, every `measuredVersion` bump, every panel resize) — and its `onNodesChange` handler (see the `measuredSizeRef` pitfall above) only ever handles `dimensions`-type changes, silently dropping the `select`-type change React Flow fires when a node is clicked. The result: clicking a Frame set its internal `selected` flag for an instant, but the very next unrelated recompute of `nodes` handed React Flow a fresh Frame object with no `selected` field, which reset it back to `false` before a person could ever see or reach the resize handles that had just appeared — reported as "there's no resize option, whatever I do," which was true in effect, since a resize handle no one can see for long enough to click on doesn't functionally exist. Scene selection never showed this problem because it was never wired through React Flow's `selected` flag to begin with — `isActive` has always been this app's own explicit `selectedSceneId` state. Fixed in v0.14.2 by giving Frame selection that same explicit treatment: a `selectedFrameId` state, set on click or drag-start and cleared on an empty-canvas click, fed into each frame node's `selected` field on every `nodes` recompute — see "Graph interaction architecture" for the fuller writeup. The general rule, sharpened from the `measuredSizeRef` pitfall above: it is not enough to remember that a controlled `nodes` prop must carry forward React-Flow-owned per-node state — every *new* per-node visual added to this graph must be checked against whether it depends on such state (`selected`, `dragging`, `measured` are the ones React Flow tracks internally) before assuming a library "built-in" behavior will just work in an app that rebuilds its `nodes` array this often. v0.15.0 generalized the fix itself, not just the rule: rather than hand-rolling click/Ctrl-click/box-select logic the way `selectedFrameId` did (an app-owned boolean, set and cleared by this app's own click/drag-start/pane-click handlers), `handleNodesChange` now applies every `select`-type `NodeChange` React Flow already emits — from a plain click, Ctrl+click, a box-select rectangle, a pane click, or Escape — into one `selectedGraphIds: Set<string>` covering both scenes and frames. React Flow already correctly implements all of that selection logic internally; the only thing this app was doing wrong was dropping the events that reported it. See "Design choice (v0.15.0)" below for why this is a different mechanism from `selectedFrameId`'s, despite solving the same class of problem.

**A controlled `NodeResizer` needs the exact same live-overlay treatment a controlled drag does — reading only `onResizeEnd` makes a resize visually fight itself while it's still in progress.** v0.15.0 investigated a report that Frame resizing "only shows the final size after releasing the mouse." `NodeResizer` itself was working correctly and firing live per-tick values the whole time (via its own `onResize` callback) — the bug was entirely on this app's side: resizing a node continuously fires the same `dimensions`-type `NodeChange` events already tracked for `measuredSizeRef` (see that pitfall above), which forced this app's `nodes` memo to recompute *mid-resize* — and, since only `onResizeEnd` updated the store, every one of those recomputes fed the frame's OLD, not-yet-committed `frame.size` back into `style.width/height` as a brand-new object, which React Flow adopted as the "real" size and snapped the box back to, immediately fighting the next resize tick trying to drag it forward again. This is structurally the same mistake `frameDrag`/`sceneDrag` already exist to prevent for dragging (see the `onNodesChange` pitfall above) — a live, in-progress interaction needs its live value fed back into the `nodes` memo, not just its final committed value — just newly discovered for resizing rather than dragging. Fixed with a `frameResize` overlay state (populated on every `NodeResizer.onResize` tick, cleared and committed to the store on `onResizeEnd`), mirroring `frameDrag`'s own shape and role exactly. **The general rule, widened once more:** any interaction React Flow reports incrementally (dragging, resizing — and, per the `XYResizer` source, any future incremental interaction library-side) needs a live overlay in this app's own state if the `nodes` memo can possibly recompute mid-interaction for an unrelated reason (and in this codebase, given how many things bump `measuredVersion`, it usually can).

**A settle-transition scoped to exclude one incremental interaction (`.dragging`) doesn't automatically exclude every incremental interaction — each one that moves a controlled value needs its own exclusion.** The `.react-flow__node:not(.dragging) { transition: transform 150ms ease; }` rule (v0.10.0, see the drag-transition pitfall above) was written when dragging was the only interaction that moved a node's `position` on every pointer-move; v0.15.0's `frameResize` overlay (immediately above) made resizing a second one, but `NodeResizer` never gets React Flow's own `.dragging` class — that class is drag-specific — so a resize (reported right after v0.15.0 shipped) that moves `position` at all, meaning any handle other than bottom-right, still had that transition applied: the position update eased over 150ms while the accompanying `style.width`/`style.height` change (a different CSS property, untouched by the `transform` transition) applied instantly, so the edge under the cursor visibly lagged while the opposite edge appeared to overshoot to compensate — exactly why bottom-right (which never touches `position`, only size) felt correct while every other handle didn't. Fixed in v0.15.1 by adding a second, resize-specific exclusion (`.scriare-resizing`, a class applied to the Frame's node object only while `frameResize` is active for it) to the same selector: `.react-flow__node:not(.dragging):not(.scriare-resizing)`. The general rule: a transition scoped to exclude "the one interaction we had in mind when we wrote this" needs revisiting every time a *new* incremental, controlled-value-driven interaction is added to this graph (see the `frameResize` pitfall above for why those keep appearing) — grep for `:not(.dragging)` and check whether the new interaction also needs adding to the exclusion, rather than assuming the existing rule already covers it.

**React Flow's own group-selection bounding box (`NodesSelection`) is a separate visual element from anything this app draws for `selected` — hiding one doesn't touch the other.** Once v0.15.0 made multi-selection actually persist (`selectedGraphIds`), React Flow started drawing its own built-in `.react-flow__nodesselection-rect` — a translucent bounding box around the whole current selection, distinct from `.react-flow__selection` (the marquee drawn *while* box-selecting, which is a different element entirely and was never in question here) and also distinct from this app's own per-node `selected`-driven styling (`SceneNode`'s accent ring, `FrameNode`'s accent border). Reported as an unwanted "blue-ish rectangle hovering the nodes" that stayed visible after a selection was made, on top of already-correct per-node highlighting. This isn't a bug in the sense the rest of this document tracks — the box is default, working-as-designed React Flow behavior (it also lets you drag the whole selection by that box) — but it visually duplicated feedback this app already provides per-node, once per-node selection persistence actually started working in v0.15.0. Fixed in v0.15.1 by hiding the box's fill/border via CSS (`background: transparent; border: none;` on `.react-flow__nodesselection-rect`) rather than trying to prevent React Flow from rendering it at all — the element still exists and its whole-selection-drag behavior still works, it's simply invisible, and per-node highlighting alone now communicates what's selected.

**Collapsing several graph nodes into one dagre node for layout purposes requires collapsing their edges too, and the collapsed node's own size has to reflect what it actually represents — otherwise dagre either can't lay the graph out at all, or lays it out at the wrong scale.** Before v0.16.0, `autoLayoutScenes` passed dagre one node per *scene*, unconditionally, and skipped any scene with a `frameId` from the position-commit step at the end — which is why a Frame containing scenes looked completely unaffected by Auto Layout (its scenes were being positioned by dagre and then that position silently discarded) while everything outside a Frame moved normally. Making a Frame participate as a first-class layout node meant three things had to change together, not just one: (1) `computeAutoLayout`'s `nodeIds` list needs one entry *per Frame-with-scenes* (not per scene inside it) plus one entry per loose scene, since dagre lays out whatever ids it's given — feeding it both a Frame's id and its contained scenes' ids as separate nodes would make dagre try to lay out five boxes for something that's visually one; (2) every edge has to be re-expressed in terms of *those same collapsed ids* — an edge between two scenes inside the same Frame becomes a self-loop (dagre can't route an edge from a node to itself meaningfully, so it's dropped entirely) and an edge crossing a Frame boundary becomes an edge to/from the Frame's own id instead of the scene's; skipping this step would either crash dagre (feeding it an edge referencing an id it was never given a node for) or silently produce nonsense positions; (3) the Frame's node has to be sized in dagre as its actual `size` (`nodeSize` callback param on `computeAutoLayout`), not the default scene-card footprint — dagre reserves rank/lane spacing based on each node's declared size, so a Frame holding six scenes given only a 180×56 footprint would get squeezed into a lane too narrow for it, overlapping its neighbors. The general rule for any future "group of things treated as one thing" layout problem in this codebase: collapsing membership, collapsing edges, and sizing the collapsed representative correctly are three separate steps that all have to happen together — doing only one (as the pre-v0.16.0 code effectively did, by skipping frame-grouped scenes' *positions* without ever removing them from dagre's *node* list) produces a silent no-op rather than a visible crash, which is exactly why this went unnoticed until a direct usability report.

**A cursor value that reads as "always active" instead of "active during this specific gesture" misleads about what's currently possible.** React Flow's own `.react-flow__pane.selection { cursor: pointer }` rule (its `style.css`) is driven by `isSelecting`, which the library sets true whenever `selectionOnDrag` is configured at all — not just while a selection drag is actually happening (`_selectionOnDrag` in `Pane`/`ZoomPane`'s own wiring). Because this app always has `selectionOnDrag` on (see "Navigation controls" in "Graph interaction architecture"), that made the canvas show a clickable-hand cursor permanently, including while just resting over empty space doing nothing — reported in Sprint 8B (v0.17.0) as part of the cursor-states evaluation, not from a bug report, since nothing was functionally broken. Fixed with a CSS override (`cursor: crosshair`) on the same selector, chosen as the conventional "drag-to-select-an-area" cursor in creative/design tools and clearly distinct from `.react-flow__node`'s own `grab`. The general rule: a state-driven cursor rule inherited from a library needs to be checked against when that state is actually true in *this app's* configuration, not assumed to only ever apply during the specific gesture its name suggests.

**Electron builds an entire application menu — with its own name and Help links — for free unless you replace it, and that default is the actual "Electron branding" a desktop app needs to hunt down.** Before v0.18.0, this app never called `Menu.setApplicationMenu()`, so Electron silently installed its own default `Menu.buildFromTemplate()` output: on macOS, that includes a top-level menu literally labelled "Electron" (Chromium reads it from the *executable's* own name absent an override, not from anything this app's `package.json` or UI ever set); on every platform, its Help submenu links out to Electron's own project site, docs, and Discord — content with zero connection to Scriare. `autoHideMenuBar` (present since v0.9.0) only hides this bar by default on Windows/Linux; Alt still reveals it, and macOS's menu bar can never be hidden at all, so this had been live, reachable Electron branding since the very first Electron scaffold, just never surfaced as a "bug" because nothing in this app's own UI pointed at it. Fixed in v0.18.0 by building and installing a real (if intentionally minimal) replacement menu on macOS — `{role: "appMenu"}` (which reads `app.getName()`, so it can't silently drift from the app's own identity again), `{role: "editMenu"}`, `{role: "windowMenu"}`, no File/Help — and removing the menu outright (`Menu.setApplicationMenu(null)`) on Windows/Linux, where Chromium's native text-input copy/paste doesn't depend on an application menu existing. The general rule: any Electron app that never explicitly calls `Menu.setApplicationMenu()` is silently shipping Electron's own default menu, not "no menu" — replacing or removing it is a one-time, load-bearing step, not an optional polish item.

**A hardcoded UI constant tuned to match a specific palette will silently drift out of sync the next time that palette is replaced wholesale, with no build error to catch it.** `main/index.ts`'s `BrowserWindow` `backgroundColor` (used to paint the window before the page has painted, avoiding a white flash) was set to `#0c0d10` with a comment naming it as matching the "Crimson Noir" theme's `--bg` — correct as of v0.9.0, when Crimson Noir was the app's only real palette. v0.12.0's Minimal redesign replaced every themed colour in the app, including `--bg`, but this one constant lives in the Electron main process, entirely outside the CSS/theme-variable system "Minimal theme architecture" describes — nothing about changing `themes.css` could possibly touch it, and no type-check or build step verifies a hex literal against a CSS custom property it's supposed to track. The drift went unnoticed for three minor versions (v0.12.0 through v0.17.0) because its only visible effect is a few-hundred-millisecond flash at launch, easy to miss and easy to misattribute to normal load latency rather than a wrong colour. Found and fixed in v0.18.0 by converting the Dark theme's actual current `--bg` (`oklch(12% 0 0)`) to its exact sRGB hex equivalent (`#060606`) via a manual OKLab→sRGB conversion, and updating both the constant and its comment. The general rule: any hardcoded value in a part of the codebase a theme/design-token system's own tooling can't reach (main-process code, native config, anything outside CSS) needs a comment naming exactly which token it's meant to track, and that comment is a standing invitation to re-verify the value whenever that token's system gets a from-scratch redesign — a "Minimal theme architecture"-scale change is exactly the moment values like this are most likely to go stale, because nothing about grepping CSS files would ever surface them.

**A UI component that doesn't reuse an existing shared shell can silently diverge from the app's established conventions with no build error to catch it — evaluating "does this look consistent" has to mean actually opening every instance, not just the ones that come to mind first.** Sprint 8D's app-wide evaluation pass (v0.19.0) found `NewProjectDialog.tsx` — the very first dialog any new user ever sees — was the one dialog in the app never migrated onto the shared `<Modal/>` component ConfirmDialogHost, MoveToDialog, and ProjectSettingsDialog were all already built on. It had its own hand-rolled `bg-black/50` backdrop instead of the `--overlay` CSS variable every other dialog reads, no `backdrop-blur`, and no window-level Escape or click-outside handling of its own — it only appeared to close on Escape because the text input inside it still had DOM focus, which is coincidental behavior, not the same mechanism `Modal.tsx`'s `keydown` listener provides everywhere else. TypeScript, `tsc --noEmit`, and a production build all pass cleanly on a hand-rolled dialog exactly as they would on one built on `Modal` — nothing about the type system or the build pipeline can tell the difference between "reuses the shared shell" and "duplicates it slightly wrong," because both are, individually, perfectly valid React. Fixed by rebuilding it on `<Modal/>`, matching every sibling dialog. The general rule: when a new UI element could reuse an existing shared component and doesn't, that's a standing, silent risk — no lint rule or type-check catches "this looks almost the same as everywhere else," and the only way to find the gap is to open every instance of a pattern side by side and compare, exactly what this sprint's category-by-category evaluation was for.

## Graph interaction architecture (v0.10.0; evaluated and polished further in v0.14.0; Frame sizing/edge-routing follow-up in v0.14.1; Frame selection fix in v0.14.2; navigation/resize/selection generalization in v0.15.0; multi-select drag and resize-transition fixes in v0.15.1; interaction-feel and micro-interactions polish pass in v0.17.0)
This section was referenced from the tech stack list above since v0.10.0 but never actually written up on its own — v0.14.0's evaluation pass is a natural point to finally consolidate it, covering both what v0.10.0–v0.10.6 built and what v0.14.0 changed on top of it. The sprint's mandate both times was explicit: **evaluate before changing.** v0.14.0 in particular was scoped as a re-inspection of the current implementation category by category, preserving every working feature and improving only what felt incomplete, inconsistent, or unpolished — not a redesign and not a new-features sprint.

**Node dragging, drag responsiveness, and drop predictability — already production-ready, untouched in v0.14.0.** Both scene and frame dragging track the cursor 1:1 on every pointer-move via the `frameDrag`/`sceneDrag` live-offset pattern (see "Known pitfalls" for the full mechanism and the several bugs it took to get there across v0.10.0–v0.10.6), gated by a 2px `nodeDragThreshold` so a plain click never registers as an accidental drag. Frame-drop detection (`findContainingFrame()`, a center-point-in-rectangle test) is deterministic and shared between the live hover highlight and the eventual commit, so what you see while dragging is exactly what happens on drop. Inspected and confirmed solid; nothing here changed.

**Lift state — frames now match the "picked up" treatment scenes always had.** A dragged scene has always lifted with an accent border, a brighter fill, and a soft shadow (`scriare-scene-card`'s `.dragging` rule, plus `scale(1.05)`). A dragged frame previously only got the generic `.react-flow__node.dragging` drop-shadow every node type gets — it read as a lesser, unfinished version of the same "this is what's moving" language. Frames now also pick up an accent border and fill while dragging, applied to `scriare-frame-box` the same way `scriare-drop-target` already is — but deliberately without the scene's `scale(1.05)`: a frame's scenes are independent, absolutely-positioned nodes, not real DOM children, so scaling the frame box alone would make its border briefly disagree with where its contained scenes actually sit mid-drag.

**Selection feedback — a selected frame is now visually distinct, and now actually STAYS selected (v0.14.2).** A selected scene has always shown a full accent border (`isActive` in `SceneNode.tsx`). v0.14.0 gave a selected frame the same accent border on the frame box itself (previously only React Flow's small `NodeResizer` handles appeared) — but that fix rode on React Flow's own internal `selected` flag, which this app's `nodes` memo never fed back in, so it was silently reset to `false` on the very next unrelated recompute (see "Known pitfalls" for the full mechanism). In effect, a Frame could never stay selected long enough for either the accent border or the resize handles to be usable — reported as "there's no resize option at all." Fixed in v0.14.2 with a `selectedFrameId` state in `FlowPanel`, set on clicking a frame (`handleNodeClick`) or starting to drag one (`handleNodeDragStart`, so grabbing a frame to move it also selects it), cleared on an empty-canvas click (`onPaneClick`), and fed into `frame.id === selectedFrameId` on every frame node object the `nodes` memo builds — the same "app-owned state, fed back explicitly" treatment `frameDrag`/`sceneDrag`/`measuredSizeRef` already got for exactly the same underlying reason. Selecting the currently-active scene now also visually extends to its edges — see the edge-behaviour entry below. v0.15.0 generalized this once more: `selectedFrameId` (a single app-tracked frame id) became `selectedGraphIds` (a `Set<string>` covering any mix of scenes and frames), populated by applying React Flow's own `select`-type `NodeChange` events instead of this app deciding selection itself in bespoke click/drag-start/pane-click handlers. Scenes now participate in this too — a scene picked up by Ctrl+click or a box-select rectangle shows a lighter accent *ring* (reusing the `--accent-ring` token), visually distinct from the stronger solid border a scene gets when it's actually open in the Scene Editor. See the new Navigation controls and Scene selection entries below. As of v0.15.1, React Flow's own group-selection bounding box (drawn automatically around the whole current selection once persistence actually started working) has its fill/border hidden via CSS — see the `NodesSelection` pitfall in "Known pitfalls" for why this doesn't touch the per-node highlighting described here.

**Hover feedback — frames now hover like scenes do.** Scene cards have always brightened their border on hover (`hover:border-[var(--border-faint)]`). Frames had no hover treatment at all — hovering one looked identical to not hovering it, unlike every other interactive surface in the app. `FrameNode.tsx` now applies the same hover border scenes use (skipped while the frame is selected, so the two states never fight for the same visual). Kept intentionally subtle, matching the existing scene hover's restraint rather than introducing a new, louder hover language.

**Edge behaviour — edges connected to the selected scene are now highlighted, and the routing itself was fixed for freely-arranged scenes (v0.14.1).** Every edge rendered identically regardless of any interaction before v0.14.0 — no hover state, no selection state — unlike a professional graph tool (Figma, Unreal Blueprint), where selecting a node typically shows what it connects to. `FlowPanel`'s edges are now built in two layers: `edgesBase` (the original, `project`-keyed memo — extraction from every scene's Tiptap content via `extractChoices()`, unchanged) and a second, cheap `edges` memo that just re-styles `edgesBase`'s existing objects (bolder stroke, `--accent` colour, slightly higher `zIndex`) for whichever edges touch `selectedSceneId` — and, as of v0.17.0, also whichever edges touch anything in `selectedGraphIds`, so an edge highlights consistently whether the scene it's attached to is open in the Scene Editor or just selected in the graph via Ctrl+click/box-select. Deliberately two layers, not one: folding `selectedSceneId`/`selectedGraphIds` into `edgesBase`'s own dependency array would re-run `extractChoices()` — a full document walk per scene — on every plain click, which is exactly the per-pointer-move cost the v0.10.3 pitfall exists to warn against, just triggered by clicks instead of drag frames. Edges themselves remain non-interactive by design (`edgesFocusable={false}`, `edgesReconnectable={false}`, `deleteKeyCode={null}`) — this only makes an edge *react* to the node it's attached to being selected, it doesn't add hover, click, or delete affordances to the edge itself, which would contradict the graph's non-destructive design. Separately, v0.14.1 fixed how an edge is actually drawn: `edgesBase` now sets `type: "default"` (bezier) instead of `smoothstep`, because a scene connected to another scene that isn't neatly to its right (the norm once Frames became a practical grouping tool with more scenes dragged freely into them) could only be drawn by `smoothstep` as a hard, looping right-angle path — see "Known pitfalls" for the full mechanism and why bezier fixes it without needing to touch the handle setup at all.

**Zoom and pan — already production-ready, untouched.** `minZoom`/`maxZoom` bounds, React Flow's default scroll-to-zoom and drag-to-pan, and the Controls widget's zoom-in/zoom-out/fit-view buttons all behave as a standard graph editor's would; nothing here showed signs of being incomplete or inconsistent, so nothing was touched.

**Cursor feedback — one real bug fixed.** `.react-flow__node { cursor: grab }` is inherited by every element inside a node's DOM, including `FrameNode.tsx`'s title `<input>` and delete `<button>` — both of which already `stopPropagation()` their own `mousedown` to prevent an actual node drag from starting, but neither had its own explicit `cursor` value, so hovering either still showed a grab-hand rather than a text-caret or pointer. See "Known pitfalls" for the general rule this establishes; fixed here with explicit `cursor-text`/`cursor-pointer` classes on the two elements.

**Frame interaction, sizing follow-up (v0.14.1) — a Frame's default and minimum size now actually fit what it's for.** v0.14.0's evaluation didn't flag Frame sizing as an issue because it wasn't asked to look at capacity, only interaction quality — a real-world usability report right after v0.14.0 shipped made clear the two are related: a Frame too small to hold more than one or two scenes undermines every other Frame interaction improvement (lift, selection, hover) just made, since there's rarely more than one scene in it to interact with at once. `buildFrame()`'s default size grew from 360×260 to 480×320, and `FRAME_MIN_WIDTH`/`FRAME_MIN_HEIGHT` (the resize-down floor) grew from 200×140 to 260×170 — see "Known pitfalls" for the general sizing-constant rule this establishes. The resize mechanism itself (`NodeResizer`, `updateFrameRect`) needed no changes — it was already correctly wired up, including correctly shifting contained scenes when resizing from the top-left handle moves the frame's origin.

**Frame interaction, selection follow-up (v0.14.2) — resizing was never actually broken; selection was.** After v0.14.1 shipped, the user reported resize handles never appeared at all, no matter what was tried — which meant the v0.14.1 sizing fix, while correct, hadn't actually been reachable in practice. Investigation traced this to a different, more fundamental bug than sizing: see the Selection feedback entry above and "Known pitfalls" for the full mechanism. Once Frame selection reliably persists, `NodeResizer`'s handles (already correctly configured with the v0.14.1 size floor) show and work exactly as intended.

**Navigation controls (v0.15.0) — right mouse button pans, left mouse button is entirely for selecting.** Before this sprint, the graph used React Flow's own default nav model: left-drag on empty canvas panned the camera, and there was no way to draw a selection rectangle at all. This is backwards from how node-based creative tools (Unreal's Blueprint editor, Blender, Figma's canvas) are usually laid out, where the left button is reserved for selection and panning is a secondary-button or modifier gesture. Changed via three `<ReactFlow>` props: `panOnDrag={[2]}` (right mouse button only — button index 2), `selectionOnDrag` (left-drag on empty canvas now draws a selection rectangle; this only activates because `panOnDrag` is no longer exactly `true`, per React Flow's own `_selectionOnDrag = selectionOnDrag && panOnDrag !== true`), and `selectionMode={SelectionMode.Partial}` (a node only needs to be touched by the rectangle, not fully enclosed, matching how box-select feels in most modern design tools — the library's own default, `Full`, requires total containment). Ctrl+click (Cmd+click on macOS) to add/remove a node from the selection needed no change at all — React Flow's own `multiSelectionKeyCode` default is already OS-aware (`Control` on Windows/Linux, `Meta` on macOS), and it was left as the default rather than hardcoded to `"Control"` so it stays idiomatic if this app is ever run on macOS. The browser's native right-click context menu is also automatically suppressed on this canvas once `panOnDrag` includes `2` — confirmed by reading `Pane`'s own `onContextMenu` handler in `@xyflow/react`'s source, which calls `event.preventDefault()` itself under that exact condition — so no extra code was needed here for that.

**Frame resize, live feedback (v0.15.0).** See the new `frameResize`-overlay pitfall above for the full mechanism (`NodeResizer`'s live per-tick values were always correct; this app's controlled `nodes` array wasn't feeding them back, so a resize fought itself mid-drag and only visibly "stuck" once released). Fixed by threading `NodeResizer`'s `onResize` (fires every tick) and `onResizeEnd` (commits) through the Frame node's `data` — the same way `renameFrame`/`deleteFrame` are threaded, except these two specifically have to live in `FlowPanel`'s own `frameResize` state (not called straight from a store hook inside `FrameNode`), because that's where the live overlay this app's controlled `nodes` memo reads has to live, mirroring `frameDrag`/`sceneDrag`.

**Scene selection vs. Scene Editor focus (v0.15.0) — a single click no longer opens a scene for editing.** Before this sprint, clicking a scene node called `selectScene` directly, immediately swapping the Scene Editor's content — which meant just glancing at, multi-selecting, or picking up a scene to drag it also discarded whatever context the writer had in the currently-open scene. This conflated two different gestures ("select this in the graph" vs. "open this for editing") into one. Fixed by removing that call from click handling entirely — a click now only participates in the (now-fixed, see Selection feedback above) graph selection — and adding it to a new `onNodeDoubleClick` handler instead: double-clicking a scene is now the explicit "open/focus this in the Scene Editor" gesture. `selectedSceneId` (the store field the Scene Editor reads) keeps its exact original meaning; only what sets it changed.

**Multi-selection drag fix (v0.15.1) — a selection of several nodes now actually moves together.** Reported immediately after v0.15.0 shipped: Ctrl+click or box-selecting several scenes correctly highlighted all of them, but dragging by one of them only moved that one node — the rest of the selection stayed visually in place even though React Flow was in fact moving them all internally. Root cause and fix are covered in full in the `onNodesChange`/live-offset pitfall in "Known pitfalls" — in short, `frameDrag`/`sceneDrag` were single-id offsets that only ever read `onNodeDrag`'s second argument (`node`, the grabbed one), never its third (`nodes`, every node actually being dragged together). Generalized into `Map<nodeId, DragOffset>`, built from `nodes` in `handleNodeDragStart` and updated from `nodes` in `handleNodeDrag`, with a matching double-commit guard in `handleNodeDragStop`: a scene whose containing Frame is *also* part of the same drag gesture is skipped in the scene-commit loop, since `updateFramePosition` already carries every scene sharing that `frameId` along with the frame — committing that scene's own position on top of that would double-apply the frame's motion. The `nodes` memo's own position computation mirrors this same precedence (a scene's containing-frame offset wins over its own individual offset, matching what actually gets committed).

**Frame resize transition fix (v0.15.1) — resizing now feels the same from every handle.** Reported alongside the multi-selection bug: resizing a Frame from its bottom-right handle felt correct, but the top-left, top-right, and bottom-left handles all had a subtle lag on the edge under the cursor, with the opposite edge seeming to overshoot to compensate. Root cause: the CSS settle-transition written for plain dragging (`.react-flow__node:not(.dragging) { transition: transform 150ms ease; }`, see "Known pitfalls") was never extended to also exclude resizing, which doesn't get React Flow's own `.dragging` class — so a resize that moves the node's `position` (any handle other than bottom-right) had that position change eased over 150ms while its `width`/`height` change applied instantly, producing the lag/overshoot. Fixed by adding a `scriare-resizing` class to the Frame's node object while `frameResize` is active for it, and excluding that class from the same transition rule. Bottom-right resizing was already correct because it never touches `position` at all — only size — so it was never subject to the transition in the first place, which is exactly why it was the one handle that already "just worked."

**Selection rectangle visual fix (v0.15.1) — React Flow's own group-selection box no longer duplicates per-node highlighting.** See the `NodesSelection` pitfall in "Known pitfalls" for the full explanation — a translucent bounding box React Flow draws by default around a multi-selection (distinct from the box-select marquee, and distinct from this app's own per-node selection styling) started actually appearing once v0.15.0 made selection persistence work, and read as unwanted visual noise once per-node highlighting was already doing that job. Fixed purely visually, via CSS, without touching React Flow's selection logic or this app's own `selectedGraphIds` state at all.

**Story Graph Interaction Feel & Micro-Interactions (Sprint 8B, v0.17.0) — a third dedicated feel pass, explicitly not a features sprint.** By this point the graph's underlying interaction *model* (drag, select, pan, resize, Frame membership, Auto Layout) had been built out and generalized across v0.10.0 through v0.16.0 — this sprint's brief was narrower and different in kind: evaluate whether each interaction *feels* like professional creative software, and polish only where it fell short, without changing what anything does or looks like at rest. Evaluated against the same eight categories the brief named (cursor states, drag feel, hover feedback, selection feedback, navigation feel, edge behaviour, auto scroll, cross-interaction consistency):

- *Cursor states* — the one real gap found was the pane's permanently-active `pointer` cursor over empty canvas (see the new cursor pitfall in "Known pitfalls"), fixed with a `crosshair` override. Every other cursor state (grab on nodes, grabbing while dragging, text/pointer on Frame's title input and delete button) was already correct and untouched — this sprint deliberately did not add cursor changes anywhere not already flagged as misleading, per the brief's "only improve clarity, don't add unnecessary cursor changes."
- *Drag feel* — dragging itself (the `frameDrag`/`sceneDrag` live-offset architecture) was inspected and confirmed already tracking the cursor 1:1 with no latency, matching the v0.14.0 evaluation's own conclusion; nothing there needed touching. What *was* missing: the scene card's own drag-lift (`scale(1.05)`) and its selection ring were snapping in and out instantly rather than easing, because `SceneNode.tsx`'s className only ever had `transition-colors`, never a `transition` covering `transform`/box-shadow. Widened to a full `transition` (150ms). Safe specifically because this transform lives on the *inner* `scriare-scene-card` div, never the outer `.react-flow__node` wrapper React Flow itself repositions every drag frame — the same "never transition a live, continuously-updating value" rule this doc has enforced since v0.10.0 (see "Known pitfalls"), applied here to confirm a *new* transition doesn't violate it, not to add an exception to it.
- *Hover feedback* — every existing hover state (scene/frame card borders, panel toggles, buttons) was already present and appropriately subtle. One real gap: a Frame's `NodeResizer` handles, visible only while the frame is selected, had no hover state of their own — every other interactive surface in the graph brightens or lifts on hover, so a static handle read as inert until actually grabbed. Fixed with a `transform: scale(1.4)` hover transition on `.react-flow__resize-control.handle`, confirmed safe against the handle's own CSS (it centers itself via `translate`, not `transform`, so the two compose independently rather than fighting each other — see "Known pitfalls" for a similar independence check on the drag-lift transform above).
- *Selection feedback* — the core per-node mechanisms (SceneNode's ring/border, FrameNode's accent border, the hidden group-selection rect) were all already correct and immediately understandable, confirmed against the v0.15.0/v0.15.1 work. The one gap was cross-cutting rather than visual: edge highlighting only reacted to `selectedSceneId` (the scene open in the Scene Editor), not `selectedGraphIds` (a scene picked up via Ctrl+click/box-select) — inconsistent with how per-node selection feedback already covers both. Broadened the edge-highlight memo's condition to check both, covered in "Edge behaviour" below.
- *Graph navigation feel* — zoom, pan, and large-graph movement were confirmed smooth and predictable, matching the "already production-ready, untouched" conclusion this doc has reached for this category since v0.14.0; nothing changed here.
- *Edge behaviour* — no flicker or delayed updates found; edges already recompute their path live off node position every frame (correctness requirement since v0.10.0, see "Known pitfalls"). The consistency gap above was fixed by widening the `isConnectedToSelected` check in the edge-styling memo to also test `selectedGraphIds`, so an edge highlights whenever either end is the Scene-Editor-open scene *or* is currently graph-selected — see "Tech stack" and the Edge behaviour entry above for the full mechanism.
- *Auto scroll* — evaluated whether dragging a node near the viewport edge auto-scrolls the canvas. Traced through `@xyflow/react`/`@xyflow/system`'s own source (`XYDrag`'s `autoPan()`/`updateNodes()`) rather than assumed: `autoPanOnNodeDrag`/`autoPanSpeed` are both already React Flow's own defaults (`true`/`15`) and this app never disabled them, so auto-panning near the viewport edge during a node drag was already working — and this app's live-offset drag architecture already correctly reflects it, since `updateNodes(lastPos)` during autoPan re-fires `onNodeDrag` with the panned canvas position, which `frameDrag`/`sceneDrag` pick up the same as any other pointer-move. Nothing was missing; both props are now declared explicitly on `<ReactFlow>` anyway, matching this codebase's standing practice of pinning any load-bearing library default rather than leaving it implicit, so a future React Flow upgrade changing its own default can't silently change this app's feel.
- *Interaction consistency* — two real inconsistencies found and corrected, both covered in "Design choice (v0.17.0)" below: the Auto Layout button's tooltip still described its pre-v0.16.0 behavior ("scenes that aren't in a frame"), and the initial camera-fit animation (300ms) and Auto Layout's own post-layout camera-fit (400ms) used two different durations for what reads as the identical gesture — unified under one `CAMERA_FIT_DURATION_MS` constant (350ms).

Per the brief's Definition of Done, none of this changes what the graph *does* — no new capability, no different visuals at rest, no changed defaults a screenshot would show. It's a felt difference, not a functional one.

## Auto Layout and Frames architecture (v0.16.0)
Auto Layout (dagre, `rankdir: "LR"`) has existed since v0.2.0, but always operated purely on scenes — a Frame containing scenes was invisible to it, so those scenes' dagre-computed positions were silently discarded at the commit step, leaving anything grouped into a Frame completely unaffected while everything else rearranged around it. Flagged explicitly by the user right after v0.15.1 shipped as the next thing to fix, with one hard constraint: the fix must not change any other Frame or Auto Layout behavior, and had to stay scoped to just this interaction.

**A Frame with at least one scene is now a first-class dagre node, sized to its own footprint.** `projectStore.autoLayoutScenes` first partitions the project's frames into `framesWithScenes` (at least one contained scene) and leaves empty frames out of layout entirely — an empty Frame is just an empty container with nothing inside it to rearrange, so including it would mean inventing a "size" for a Frame Auto Layout has no actual reason to touch, and changing its position for no visible reason is exactly the kind of surprising side effect the user's constraint ruled out. Scenes are similarly split into those grouped into an included Frame and `looseScenes` (no `frameId`, or a `frameId` pointing at a stale/deleted Frame). `computeAutoLayout` is then called with one node id per Frame-with-scenes plus one id per loose scene — never one id per scene inside a Frame — and a `nodeSize` callback that returns that Frame's actual `size` for a Frame id (falling through to `computeAutoLayout`'s existing default scene-card footprint for a loose scene id). This is what makes dagre reserve real, correctly-scaled space for a Frame's whole cluster instead of squeezing it into one scene-card-sized box or, worse, ignoring it.

**Edges are collapsed onto the same ids nodes were collapsed onto — self-loops dropped, cross-boundary edges retargeted.** A `layoutNodeIdForScene()` helper maps every scene id used in an edge to whichever id actually represents it in this layout pass: its containing Frame's id, if that Frame was included; its own id, if it's a loose scene; or `undefined`, if it references a scene that no longer exists (defensive against already-stale data, not a new failure mode this milestone introduces). An edge where both ends map to the same id (two scenes inside the same Frame connecting to each other) is a self-loop from dagre's perspective and is dropped rather than passed through — dagre has no meaningful way to lay out an edge from a node to itself, and this edge doesn't need to influence Frame-to-Frame layout anyway, since it's entirely internal to one Frame's own arrangement. An edge crossing into or out of a Frame becomes an edge to/from that Frame's collapsed id instead of the scene's own id, so dagre still accounts for the actual connectivity between Frames and loose scenes, just at the granularity layout now operates on. Duplicate edges produced by this collapsing (two different scene-to-scene connections both crossing the same Frame boundary) are deduplicated via a `seenEdges` Set before being handed to dagre, since dagre only needs to know a connection exists once per direction to route around it.

**A Frame's contained scenes move together as a group, preserving their exact relative arrangement — they are never independently repositioned by dagre.** Once dagre returns a new position for each collapsed id, committing the result is a two-pass shift rather than a per-scene position write: first, for every Frame that was included in this layout, its `dx`/`dy` delta (new dagre position minus its old one) is computed and its `Frame.position` is updated; second, every scene contained in a repositioned Frame is shifted by that *same* `dx`/`dy` — not given a new position of its own — while a loose scene is written directly to its own new dagre position. This mirrors the existing "shift the frame, carry its scenes by the same delta" pattern `updateFramePosition`/`updateFrameRect` already use for a manual Frame drag or resize (see the core data model's "always absolute" design choice), rather than introducing a second, different way of moving a Frame's contents. It's also the mechanism that satisfies the user's constraint directly: since every scene inside a Frame moves by the identical delta the Frame itself moves, the *relative* positions the writer arranged inside that Frame — which scene sits where, relative to its neighbors — never change, no matter where Auto Layout decides to place the Frame as a whole on the canvas.

**What this deliberately does not touch.** Manual Frame drag and resize (`frameDrag`, `frameResize`, `updateFramePosition`, `updateFrameRect`) are untouched — Auto Layout calls none of that code, it only ends up writing to the same `Frame.position`/`Scene.position` fields those mechanisms also write to. Frame membership assignment (`findContainingFrame()`, run on scene drag-stop) is untouched — Auto Layout never adds or removes a scene's `frameId`, it only respects whatever grouping already exists at the moment the button is pressed. A loose scene's own Auto Layout behavior is byte-for-byte the same as before this milestone — the `nodeSize` callback returns `undefined` for a loose scene id, which falls through to `computeAutoLayout`'s pre-existing default, so nothing about how an ungrouped scene gets positioned changed at all.

## Content Browser architecture (v0.5.0)
The left panel ("Content", formerly "Scenes") is built to stay generic as new content types are added later, per an explicit requirement to avoid hardcoding Story-specific logic. Two node kinds make up `Project.content` (a flat array, same "flat list + parentId/order" style as graph Frames use, not nested JSON):
- **ContentFolder** — pure organization, never holds data: `{ id, kind:"folder", category, parentId, order, name, color?, icon?, tags? }`.
- **ContentLeaf** — a reference to a real entity living elsewhere, never a copy: `{ id (= the referenced entity's id), kind:"leaf", category, parentId, order, refType }`. Today `refType` is only `"scene"`, referencing `project.scenes`.

`category` is `"story" | "characters" | "locations" | "notes" | "assets"`. Only `"story"` has real leaves; the other four render in the browser as always-empty, expandable "Coming soon" placeholder roots with no backing entities yet — adding a real Characters editor later means adding a new `refType` and an editor for it, not touching the tree, its drag-and-drop, its search, or its Favorites system.

**Favorites** are a fully separate, generic reference list: `Project.favorites: { id, refType, refId }[]`. Favoriting never moves or duplicates anything; any current or future content type can be favorited just by adding an entry with its `refType`.

**Folder deletion ungroups, never destroys**: a deleted folder's children move up to its parent, the same rule graph Frame-deletion already followed. **Scene deletion** additionally removes that scene's `ContentLeaf` and any favorite referencing it, so nothing dangling is left behind.

Drag & drop, reordering, and moving into/out of folders all go through `moveContentNodes(nodeIds, newParentId, newIndex)` (generalized in v0.6.0 to accept one or many ids at once; the original single-id `moveContentNode` now just delegates to it), which recomputes `order` (plain 0..n-1 per parent, no fractional-order bookkeeping) for both the source and destination sibling lists. `isDescendant()` refuses a move that would nest a folder inside its own descendant.

The UI (`ContentBrowser.tsx` + recursive `ContentTreeRow.tsx`) shares its callbacks and lookups down through a React context (`contentBrowserContext.ts`) rather than prop-drilling through every recursion level — a deliberate choice given how many interactions (rename, drag state, context menu, expand/collapse, favorites, multi-selection, and as of v0.8.0 which scene is the Start Scene) a single row needs access to.

Expand/collapse state (which folders in the tree are expanded) and the editor/graph split height are both personal layout preferences kept in `localStorage`, not the project file — consistent with how Play Mode state and the splitter height already work. As of v0.11.0, whether the whole Content panel itself is docked away or expanded is a separate, similarly-persisted preference — see "Dockable layout architecture" above; the two are independent (a writer can keep the tree's own expand/collapse state exactly as they left it, and only toggle whether the panel itself is visible).

## Desktop UX polish architecture (v0.6.0)
This milestone added no new data model — it made the existing Content Browser behave like a standard desktop file explorer, and replaced every native OS confirmation dialog with an in-app one.

**Confirm dialogs.** `confirmDialogStore.ts` is a small Zustand store exposing `confirmDialog(options): Promise<boolean>` — any component (including ones deep inside the React Flow canvas, like `FrameNode.tsx`) can `await confirmDialog({...})` without prop-drilling a dialog's open/close state. It queues at most one pending request and resolves the caller's promise when the single globally-mounted `<ConfirmDialogHost/>` (rendered once in `App.tsx`, above everything including Play Mode) is dismissed. Both it and the new `MoveToDialog` are built on a generic `<Modal/>` shell: dark theme, rounded corners, backdrop blur/dim, click-outside-to-close, Escape always cancels, Enter confirms where applicable. (As of v0.9.0, `<Modal/>` accepts an optional `widthClassName` prop, still defaulting to the original compact width, so a bigger dialog like Project Settings' Appearance grid can opt into more room without affecting the others.)

**Multi-selection.** `ContentBrowser.tsx` keeps `selectedIds: Set<string>` and a `selectionAnchor: string | null`, separate from `selectedSceneId` (the one scene open in the editor). `handleItemClick` implements desktop-standard semantics: a plain click replaces the selection with just that item and performs its normal action (toggle a folder, or open a scene); Ctrl/Cmd+click toggles one item in/out of the selection with no side effect; Shift+click selects every item between the anchor and the clicked item, in the exact order they're currently rendered (`flattenVisible()` in `contentTree.ts` walks the tree honoring which folders are expanded, so the range always matches what's on screen). Right-clicking an item outside the current selection first collapses the selection down to just that item, so the context menu's bulk/single decision is always based on what's visually highlighted. As of v0.6.1, tree rows also suppress the browser's native text-selection and click-focus outline, since Shift+Click was triggering a stray focus/selection highlight on the clicked row as a side effect of the modifier key — originally via `select-none` plus an `onMouseDown={(e) => e.preventDefault()}` on the row's inner `<button>`s, but that `mousedown` handler silently broke native drag & drop for the whole row (see "Known pitfalls"); as of v0.8.3 the highlight is suppressed by `select-none` and `focus:outline-none` alone, with the inner controls changed from `<button>` to `<div role="button">` and the `mousedown` handler removed.

**Multi-item drag & drop.** `draggingIds: Set<string>` replaced the old singular `draggingId`. Starting a drag on an item that's already part of a selection of more than one drags the whole selection; dragging an unselected item drags (and selects) just that one. Both paths end up at the same generalized `moveContentNodes(nodeIds, newParentId, newIndex)`, so a multi-item drag between folders is exactly as consistent as a single-item one.

**Multi-item actions.** The context menu (`ContentBrowser.tsx`'s `buildMenuItems`) branches on whether the right-clicked node is part of a selection of more than one. The bulk branch offers: **Move N items…** (opens `MoveToDialog.tsx`, a simple list of every Story folder plus the Story root, filtered to exclude the moving items and any folder that's their descendant); **Duplicate** (only shown when the selection contains scenes, via the new `duplicateScenes(sceneIds)` store action); **Favorite/Unfavorite** (via the new `setFavorites(refType, refIds, value)`, which sets rather than toggles — so a mixed selection always ends up either fully favorited or fully unfavorited, never inconsistently toggled); and **Delete** (via `confirmDialog` + the new `deleteContentNodes(nodeIds)`, which mixes folder-ungrouping and scene-deletion in one pass, resolving a deleted node's surviving parent by walking up through any chain of folders that are also being deleted in the same operation).

**Preserved behavior.** Single-item deletion of a scene or a folder is unchanged in effect (folder deletion still ungroups rather than destroys) — only the confirmation UI changed, from `window.confirm` to `confirmDialog`. The Content Browser's layout, header, search, and Favorites section were not touched.

## Reading-column consistency (v0.6.2)
The writing editor and the Play runtime both render the same scene content, but through two different renderers — a live ProseMirror editor vs. a one-shot `generateHTML()` string — and each had grown its own copy of the "reading column" wrapper (centered, width-capped, prose typography). `utils/readingColumn.ts` now defines that once: `READING_COLUMN_CLASS` (`"mx-auto w-full max-w-2xl"`, centers and caps the column at the same width regardless of how much horizontal space the surrounding layout gives that screen — Play Mode has more, since the Content Browser and Inspector are hidden while playing, but the column itself stays the same width) and `READING_PROSE_CLASS` (`"prose prose-invert max-w-none break-words"`, the same Tailwind Typography classes both already used, now with `break-words` added so a long unbroken token wraps inside the column instead of overflowing it; as of v0.12.0 also `font-reading`, pinning the column's font independently of the app-wide default — see "Minimal theme architecture"). `SceneEditor.tsx` and the Play runtime both import these instead of hardcoding their own copy, so the two can't silently diverge again. This was a pure rendering-consistency fix — no change to Play Mode's layout, navigation, or choices.

## Narrative Blocks architecture (v0.7.0)
The explicit constraint behind this milestone: Scriare stays a rich text editor. Narrative elements are embedded *inside* the document — writers still type through a Choice Block or a Callout exactly like they'd type past an inline image in Word, never dropped into separate cards à la Notion.

**Choice Block became multi-option.** `choiceBlock`'s attrs changed from a single `{choiceId, text, targetSceneId}` to `{blockId, options: ChoiceOption[]}`, where `ChoiceOption = {id, text, targetSceneId}` (defined in `utils/choiceBlocks.ts`). `ChoiceBlockView.tsx` renders one row per option (text + destination `<select>` + remove), a "+ Add option" button, and ▲/▼ buttons per row to reorder — all inside one atomic block, so "add another path" never means inserting a second block. `extractChoices(content)` still walks the whole document and returns the same flat `Choice[]` every existing consumer (the graph's edges, Auto Layout, the Inspector's Outgoing Choices summary) expects — it just now flattens every option out of every block instead of reading one option per block, so none of those consumers needed to change.

**Play Mode plays back every block in document order — including choices.** Previously Play Mode called `stripChoiceBlocks()` to remove every Choice Block before `generateHTML()`, then rendered every scene's choices as one group of buttons at the bottom, regardless of where they were written. That directly contradicted "the player's reading experience should match the author's writing experience," so it's gone. The document is instead split into ordered segments — a run of ordinary blocks or a single interactive block — alternating exactly as they appear in the document (as of v0.8.0 this logic lives in `runtime/documentSegments.ts`, generalized beyond just Choice — see "Runtime architecture" below). A scene still shows "The End" + Restart, but only computed from whether *any* option anywhere in the scene has a destination (`extractChoices(...).some(c => c.targetSceneId)`) — the check didn't need to change, only where the buttons themselves render.

**Slash commands are Tiptap's own `Suggestion` utility, not a bespoke system.** `extensions/SlashCommand.ts` is a small `Extension` whose only job is registering a `Suggestion` ProseMirror plugin (`@tiptap/suggestion`) triggered by `"/"`. Its `items()` filters the Narrative Blocks registry by title/keywords against whatever's typed; its `render()` mounts `components/editor/SlashCommandMenu.tsx` via `ReactRenderer` (from `@tiptap/react`) into a `position: fixed` div positioned at the caret's `clientRect()` — no extra positioning library. Arrow keys/Enter reach the menu through `Suggestion`'s `onKeyDown` lifecycle hook forwarding to the menu's own imperative handle (`useImperativeHandle`), the same pattern Tiptap's own mention-menu examples use. Selecting an item deletes the `/query` text and calls that item's own `command(editor, range)`.

**The registry is the whole extensibility story — for authoring.** `narrativeBlocks/registry.ts` exports `NARRATIVE_BLOCKS: NarrativeBlockDefinition[]` — `{id, title, description, icon, keywords, command}` — and that array is the single source both the slash menu's item list and its filtering read from. Choice's command calls the ChoiceBlock extension's own `insertChoiceBlock()`; Divider and Quote call the existing `setHorizontalRule()`/`toggleBlockquote()` commands (no new node types for either); Callout calls the new `toggleCallout()`. A future block (Variables, Conditions, Images, Dialogue, Audio, an embedded widget) is meant to add one entry here plus its own Tiptap extension registered in `SceneEditor.tsx` — the slash menu, its keyboard handling, and its filtering never need to change. Its *playback* behavior is a separate registry — see "Runtime architecture" below.

**Callout needs no custom rendering code at all.** It's `Node.create({name: "callout", content: "block+", ...})`, structurally identical to Blockquote — Tiptap's default editable NodeView handles it in the live editor, and `generateHTML()` handles it in the Play runtime, both via the same `renderHTML()`/`parseHTML()`. All of its visual identity (background tint, left accent border, 💡 icon) is one CSS rule in `styles/index.css` targeting `[data-type="callout"]`, so it looks identical wherever that attribute shows up in the DOM — no per-renderer styling to keep in sync (see "Known pitfalls").

**Migration.** Two shapes of old content exist in the wild: pre-v0.4.0 files with a separate `scene.choices` array (no `choiceBlock` nodes at all), and v0.4.0–v0.6.x files whose `choiceBlock` nodes are already in the tree but in the old single-option shape (`{choiceId, text, targetSceneId}`, no `options` array). `normalizeProject()` runs `migrateLegacyChoiceBlocks(content)` first (upgrades any old-shape node into `{blockId, options: [...]}`, one option carried over, no-op if already current-shape), then the existing legacy-`scene.choices`-into-content migration (which now builds new-shape nodes directly) only if the scene still has zero choices after that. Both migrations were verified against representative fixtures of each old shape before this was shipped.

## Runtime architecture (v0.8.0, extended v0.8.1)
This sprint's explicit goal was making Play Mode *feel* like a polished, built-in runtime — pressing ▶ Play should feel like pressing Play in a game engine — without adding any new writing features. Most of "Runtime Fidelity" (headings, rich text formatting, colors, highlights, alignment, all narrative blocks in exact document order) already held as of v0.7.0, since the player was already a static `generateHTML()` render sharing the editor's own extension set. What this sprint changed was structural separation, plus the missing runtime-specific features.

**The runtime is now its own layer, under `src/renderer/src/runtime/`.** `PlayRuntime.tsx` (replacing `components/play/PlayView.tsx`) is the player component; it never imports an editor UI component (`SceneEditor`, `EditorToolbar`, `ChoiceBlockView`, `SlashCommandMenu`) — only the document types, Tiptap's `generateHTML()`, and the runtime's own registry. This was already almost true in practice; moving it into its own folder makes the boundary a matter of import paths, not just convention.

**A registry, mirroring `NARRATIVE_BLOCKS`, but for playback.** `runtime/types.ts` defines `RuntimeBlockDefinition` (`{nodeType, render}`) and `RuntimeContext` (today just `{goToScene}` — the one capability a block's render function can call back into the player with; extending this object, not every block's signature, is how a future block gains a new capability). `runtime/registry.ts` holds `RUNTIME_BLOCKS`, currently just `choiceRuntimeBlock` (`runtime/blocks/choiceRuntimeBlock.tsx`). Adding a future block (Variables, Conditions, Images, Dialogue, Embedded widgets) means adding one more registry entry and its own file under `runtime/blocks/` — never touching the render loop itself. `runtime/documentSegments.ts` generalizes what `splitContentByChoiceBlocks` did in v0.7.0: it splits a scene's top-level content into ordered `{kind:"prose"}` / `{kind:"block"}` segments using `RUNTIME_BLOCK_TYPES` (derived from the registry) instead of a hardcoded check for `choiceBlock`, so a scene still renders top-to-bottom exactly as written, and any future runtime block automatically gets its own segment the moment it's registered.

**Start Scene.** `Project.startSceneId` already existed (set to the first scene on project creation, reassigned automatically if that scene is deleted) but had no explicit UI to change it until v0.8.0's `ProjectSettingsDialog.tsx` (opened from the top bar's ⚙ button) added a scene picker. v0.8.1 added two more entry points that all write the exact same field through the exact same action: a **"Set as Start Scene"** item in the Content Browser's per-scene context menu (`ContentBrowser.tsx`'s `buildMenuItems`, hidden when that scene is already the Start Scene, since there'd be nothing to do), and a **"This is the Start Scene"** checkbox in the Inspector (`InspectorPanel.tsx`) that can also *clear* it (unchecking calls `setStartScene(null)`, which falls back to the first Story scene — the same fallback an unset project always had). `projectStore.setStartScene(sceneId: string | null)` is the single action behind all three surfaces; because `startSceneId` is one field on `Project` rather than a flag duplicated per scene, "only one Start Scene may exist" and "all three UIs stay synchronized" are true by construction, not by anything that needs separate enforcement (see "Known pitfalls"). The Start Scene is indicated with a small "▶ Start" pill badge (`components/common/StartBadge.tsx`) rather than Twine's rocket icon — shown in both the Content Browser row and the graph's `SceneNode`, matching Scriare's existing rounded-pill visual language (the same family as the favorite ★ and Choice Block's own styling) instead of introducing a new icon convention.

**End Scene experience.** The ending screen (still gated on "no option anywhere in this scene has a destination") is now a centered, minimal card with **Restart Story** and a new **Return to Editor** button (`exitPlay`), instead of a bare heading and a single button.

**Runtime navigation.** Escape now exits Play in addition to the existing Exit Play button, both calling the same `exitPlay()` action. Neither needed to restore anything explicitly: the editor and graph were already never unmounted while playing (App.tsx only CSS-hides them), so the current scene, scroll position, graph pan/zoom, and selected scene all survive untouched — this was true before v0.8.0 and is unchanged, just now explicitly verified as part of this sprint's requirements.

**Runtime polish.** A single CSS keyframe (`runtimeFadeIn` / `.runtime-scene-fade` in `styles/index.css`) fades each scene in on change — applied by keying the scene's wrapper `<div>` on `scene.id` inside `PlayRuntime.tsx`, so React's own remount-on-key-change does the animation triggering; no transition library needed for "simple fade is enough."

## Desktop Identity architecture (v0.18.0)
Sprint 8C's first section asked a question none of the graph-focused sprints (8A/8B) had reason to ask: does the app present itself to the operating system as "Scriare," or does it still leak "Electron" somewhere the writer can see? Evaluated item by item against the sprint brief's own checklist.

**Window title, window icon — already correct, confirmed and left untouched.** `renderer/index.html`'s `<title>` has read "Scriare" since early in the project; `BrowserWindow`'s `icon` option has pointed at the real logo-derived `build/icon.png` since v0.13.0's "Real Logo architecture." Neither needed any change — both were already checked directly rather than assumed.

**App identity (`app.getName()`) — was silently wrong, now explicit.** `package.json`'s `"name"` field is `"scriare"`, all lowercase — the npm-package-name convention, never meant to be display text. Absent an explicit override, that's exactly what Electron's `app.getName()` returns, and `app.getName()` is what several native surfaces read from by default (a macOS app-menu role, `app.setAboutPanelOptions()` if it were ever left to infer a name, native dialog titles). `app.setName("Scriare")` is now called at the very top of `main/index.ts`, before anything else touches app identity — Electron's own docs note several of these APIs only pick up a name set this early.

**Native application menu — the real "Electron" branding leak, found and removed.** This app never called `Menu.setApplicationMenu()`, so every launch silently ran on Electron's own default menu — literally labelled "Electron" on macOS, and carrying a Help submenu linking to Electron's own site/docs/Discord on every platform. See the new pitfall entry in "Known pitfalls" for the full mechanism. Fixed with `buildApplicationMenu()`: a minimal three-role menu (App/Edit/Window) on macOS, where the menu bar can't be hidden and needs a real replacement; no menu at all (`null`) on Windows/Linux, where `autoHideMenuBar` already keeps it out of the way and Chromium's native copy/paste doesn't depend on an application menu existing.

**About panel — was Electron's own generic default, now Scriare's.** No code in this app had ever called `app.setAboutPanelOptions()`, so macOS's native About panel (reachable from the Scriare/Electron app menu regardless of what this app's own UI shows) fell back to Electron's own generic name/icon. `app.whenReady()` now calls `app.setAboutPanelOptions({applicationName: "Scriare", applicationVersion: app.getVersion(), version: app.getVersion(), copyright: "© Volkan"})`.

**Windows taskbar identity — set proactively, ahead of packaging.** `app.setAppUserModelId("com.volkan.scriare")` gives Windows a stable identity for taskbar grouping, pinning, jump lists, and toast notifications, independent of whatever the built executable happens to be named. This matters most once the app is actually packaged and installed (see "What's deliberately deferred" below), but costs nothing to set now and is already correct for anyone testing an unpackaged dev build on Windows.

**Window background-color flash — a real, if narrow, cross-check with the theme system.** `BrowserWindow`'s `backgroundColor` (painted before the page itself has rendered, to avoid a flash of the wrong colour) had drifted out of sync with the actual current Dark theme background since v0.12.0's Minimal redesign replaced the palette this constant was tuned for — see the new pitfall entry in "Known pitfalls" for the full mechanism, including the OKLab→sRGB conversion used to derive the correct value. Fixed (`#0c0d10` → `#060606`). Deliberately not made theme-aware in this sprint — see "What's deliberately deferred" below.

**What's deliberately deferred, and why.** Two items from the sprint brief's own checklist are real gaps this sprint chose not to close, for reasons specific to each:
- **Task Manager process name and executable metadata.** An unpackaged Electron dev build's process is, and will always be, named after the `electron` binary itself (`electron.exe`/`Electron`) — this has nothing to do with any code this app writes, and nothing short of actually packaging the app (via `electron-builder` or an equivalent, setting `productName`/`appId`/icons/code signing) changes it. This project has no `electron-builder` devDependency or build configuration at all yet, so fixing this now would mean standing up an entire build pipeline as a side effect of a UI-polish sprint — exactly the kind of scope creep the brief's own "avoid temporary workarounds" instruction warns against. This is real, necessary future work, not an oversight; it belongs in a dedicated packaging/release-prep pass.
- **A fully theme-aware window background.** The `backgroundColor` fix above corrects today's default (Dark) but is still, structurally, a single static guess — a writer using Light mode still sees a brief dark flash before the page paints. The active theme choice lives in the renderer's `localStorage`, which the main process has no visibility into at window-creation time; making this genuinely theme-aware would need an IPC round-trip (persist the theme choice somewhere the main process can read before creating the window, or have the renderer signal it early enough to matter) — a real, if small, architectural addition, not a constant to tweak. Left as a named opportunity rather than attempted as a partial fix.

## Existing Features Evaluation & Final Polish architecture (Sprint 8D, v0.19.0)
This is the final pass of the Sprint 8 arc: with the desktop shell evaluated in Sprint 8C (v0.18.0) and the Story Graph evaluated three times over (v0.14.0, v0.17.0, and its own earlier passes), this sprint asked the same "evaluate before changing" question of every remaining named system in the app — the Rich Text Editor, its toolbar, Choice Block, the Content Browser (including its context menu, drag & drop, and folder/scene management), Scene Details/Inspector, Project Settings, Play Mode, Dialogs, Popups, Context Menus, Keyboard Shortcuts, and the Start Scene workflow — plus a simulated end-to-end workflow (create project → create folder → create scene → write → insert Choice Block → reorganize Content Browser → open Story Graph → navigate → play → save → reopen) to surface friction a category-by-category read alone wouldn't catch. The explicit instruction was to leave anything already production-ready alone and fix only concrete, nameable UX/consistency/usability gaps — not to polish for its own sake.

**Fifteen of sixteen evaluated systems needed no change.** The rich text editor and its toolbar, Choice Block (its `--danger` fix already landed in Sprint 8C), the Content Browser's selection/drag-drop/context-menu/folder logic, the Story Graph (explicitly out of scope here — already evaluated three separate times, and `FlowPanel.tsx`'s documented memo/dependency-array fragility, see "Known pitfalls," makes it a no-touch-without-extreme-care zone for a broad polish sprint), Scene Details/Inspector, Project Settings, Play Mode, the confirm dialog, the slash-command popup, context menus (already fixed in Sprint 8C), keyboard shortcuts, drag & drop, folder management, scene management, and the Start Scene workflow's four entry points (all four read the same `startSceneId` field, so they can never disagree by construction — see "Known pitfalls") were each inspected and found consistent with the rest of the app's established interaction language. Nothing in any of these was touched.

**One real gap: `NewProjectDialog.tsx` was the sole dialog never migrated onto the shared `<Modal/>` shell.** See "Known pitfalls" for the full mechanism and "Design choice (v0.19.0)" for why the fix was scoped exactly to that one file. Because this is the very first dialog any new user of the app ever sees, the inconsistency (a non-token backdrop colour, no blur, unreliable Escape/click-outside dismissal that only appeared to work because the input retained focus) was more visible than most latent inconsistencies would be, despite being a small, mechanical fix once found.

**Workflow simulation surfaced no friction beyond the dialog above.** The full create → write → graph → play → save → reopen loop was walked through as the brief specified; the New Project dialog issue sits at step 1 of that loop, and nothing downstream of it (folder/scene creation, Choice Block insertion, Content Browser reorganization, Story Graph navigation, Play Mode, save/reopen) showed a dead click target, a missing feedback state, or an inconsistent affordance.

**Technical debt identified but deliberately left for a future sprint, per the "don't polish for the sake of polishing" instruction:** `EditorToolbar.tsx`'s highlight-tool icon uses a literal amber colour rather than a theme token — flagged as a judgment call (it may be representational of an actual highlighter colour, not a themed-chrome inconsistency) rather than guessed at; the native `<input type="color">` swatches in `EditorToolbar.tsx`/`ChoiceBlockView.tsx` use raw hex values, which is correct as-is since those are the writer's own content colours, not app chrome, so no `--variable` applies; `EditorGraphSplit.tsx` and `ContentBrowser.tsx` each maintain their own separate `localStorage` try/catch pattern rather than sharing one helper — a minor non-unification, not a bug; and `TopBar.tsx`'s Export button remains a disabled stub ("Coming in a later milestone"), correctly out of scope for a polish-only sprint.

Design choice (v0.9.0): the active theme id lives in its own `themeStore.ts`/`localStorage`, not on `Project` or inside `projectStore`. It's a display preference of the person using the app on this machine, not a property of the story file itself — the same reasoning already applied to the editor/graph split height and Content Browser expand state. A story opened on a different machine (or by a different person) should not force a colour scheme on them.

Design choice (v0.11.0): panel-collapse state is one object (`PanelCollapseState`) in `App.tsx`, not three independent booleans scattered across components. Consolidating it is what let it be persisted in one `localStorage` write per toggle rather than three separate keys — and, more importantly, it's the same "one place, not several that could drift" reasoning used elsewhere in this doc (`startSceneId`, `READING_COLUMN_CLASS`): a future fourth dockable panel adds one more key to this same object and one more `togglePanel()` call site, not a parallel bookkeeping mechanism.

Design choice (v0.11.1): all three panels' collapse toggles use one shared icon family (a solid triangle) and sit at the same relative position (the boundary edge nearest the editor), rather than each panel inventing its own convention. Consistency-of-presentation bugs like this are easy to miss piecemeal (each panel's toggle looked "fine" in isolation when it shipped) but read immediately as sloppy once panels are used side by side — the fix here is purely visual/positional, no new state or props beyond what v0.11.0 already introduced.

Design choice (v0.11.2): a collapsed panel's label is treated as an instance of the app's existing "section header" pattern (bold, uppercase, letter-spaced), not a one-off bit of text — so any future collapsed panel should copy that same class trio rather than reinventing a label style. This is the same lesson as v0.11.1's icon/placement fix, just applied to typography instead of shape/position: a UI pattern that already has a convention elsewhere in the app should be matched exactly, not approximated.

Design choice (v0.12.0): `--accent` is deliberately the *only* colour variable that changes between the two themes' "brand" role, and it's set to a plain inversion of `--bg` rather than a hand-picked hue — so "accent" and "neutral, high-contrast UI element" are the same thing by construction, and there's no way for a future theme edit to accidentally reintroduce a colour into a spot that's supposed to be monochrome. Genuine colour (`--danger`, `--success`) lives in entirely separate variables that no generic "accent" call site reads, so a component has to opt in deliberately (as `ConfirmDialogHost.tsx` does via its `danger` prop) rather than opting in by accident. This is the direct opposite design choice from v0.9.0's `--accent` (a real hue, meant to be visually distinctive per theme) — both are "one variable, every component reads it," just pointed at a different job.

Design choice (v0.12.0): `--success` and `.font-technical` (IBM Plex Mono) are both defined but deliberately left unused in this delivery, rather than retrofitted onto the nearest existing UI element to "use" them. Forcing green onto Play/Create Project/Move-here/Restart (the app's existing primary-action buttons) would have applied colour to actions that aren't semantically "Apply" just to give the new token a call site, working against the "minimal by default, colour only where it's earned" goal the request set. Infrastructure defined ahead of a clear use is an established pattern in this codebase already (`--danger` sat unused from v0.9.0 until v0.12.0's `ConfirmDialogHost.tsx` fix gave it a real caller); the alternative — inventing a use case to justify a token — tends to produce the wrong use case.

Design choice (v0.12.1): a reported "too close to pure white" complaint about a single tier (`--bg`) was fixed by shifting every affected tier in Light mode by the same 4-point lightness step, not by lowering `--bg` in isolation. See "Known pitfalls" for why: a fixed elevation scale (bg < surface < surface-2 < surface-3 in Dark, the mirror image in Light) needs its *relationships* preserved, not just its most-complained-about member adjusted.

Design choice (v0.13.0): the Dark/Light naming on the supplied logo files was treated as "which app background this variant is designed to sit on" and confirmed by actually compositing each variant against Scriare's real `--bg` values before wiring it into `BrandMark.tsx`, rather than assumed from the filename alone or from which fill color is visually dominant. A plausible alternative reading (e.g. "Dark" meaning "the mostly-dark-colored version," independent of what background it's used on) would have produced the opposite, wrong mapping for this particular artwork, since Primary Dark's dominant fill and its intended-background reading happen to point the same direction only by design intent, not by any rule that could be inferred from color alone.

Design choice (v0.13.0): Icon Dark was used for the OS-facing app/taskbar icon regardless of the app's own theme setting, per an explicit instruction, rather than swapping Icon Dark/Icon Light the way the in-app logo swaps Primary Dark/Primary Light. An OS taskbar or window-manager icon isn't aware of an in-app `data-theme` attribute the way a React component reading `useThemeStore` is — making it theme-aware would need main-process code to read the renderer's persisted theme choice and regenerate/re-set the window icon at runtime, a meaningfully bigger change than this request asked for, and not what was requested.

Design choice (v0.14.0): a dragged Frame gets the same accent-border-and-fill "lift" language a dragged Scene does, but deliberately not the same `scale(1.05)`. A Scene node's visual content is entirely inside its own box, so scaling the whole box during a drag reads as "this object is being picked up." A Frame's "content" (its contained scenes) lives in separate, independently-positioned nodes that don't scale with it, so scaling the frame box alone would create a visible mismatch between the frame's boundary and where its scenes actually sit for the duration of the drag — worse than the plain drop-shadow it replaced. Matching a design pattern's *intent* (draw attention to what's moving) sometimes means deliberately not copying every part of its *implementation*.

Design choice (v0.14.0): edge selection-highlighting is computed in a second memo layered on top of the existing project-keyed `edgesBase`, rather than folding `selectedSceneId` into that memo's own dependency array. The existing memo's cost (a full `extractChoices()` walk per scene) is the exact one flagged in the v0.10.3 pitfall as too expensive to run on every drag frame — adding a dependency that changes on every plain click would reintroduce that same cost at click-frequency instead of drag-frequency, a different trigger for the identical mistake. Splitting "what the edges fundamentally are" from "how the edges are styled right now" keeps the expensive computation keyed only to what actually changes it (scene content), matching how `nodes`/`edges`/`choiceCountByScene` were already split apart for the same reason back in v0.10.3.

Design choice (v0.14.1): edges switched from `smoothstep` to `default` (bezier) rather than redesigning `SceneNode`'s handle setup (adding more handles, or making handle side depend on relative node position). The looping artifact's actual cause was the edge *type*'s routing constraint (axis-aligned only), not the handles themselves — the existing fixed Left/Right handles are exactly what a bezier curve needs to draw a smooth line from any relative direction, so the fix is one line (the `type` string) rather than a new handle architecture. This follows the sprint's own "polish what exists, don't build a duplicate system" mandate literally: the smallest change that fixes the actual mechanism, not the biggest change that could plausibly also fix it.

Design choice (v0.14.1): Frame's default and minimum size were raised together, not just one or the other. Raising only the default (leaving the resize floor at 200×140) would still let a frame be shrunk back down to uselessness after creation; raising only the floor (leaving the default at 360×260) would leave every newly-created frame just as cramped as before until the writer thought to resize it. Both numbers exist to answer the same question — "how small can a Frame usefully be" — so both needed the same fix, echoing this doc's earlier lesson (v0.12.1) about editing a value's full relationship to its purpose rather than just the part someone happened to complain about.

Design choice (v0.14.2): Frame selection was given its own explicit `selectedFrameId` app state rather than trying to make React Flow's built-in `selected` flag survive by, say, adding a `select`-type branch to `handleNodesChange`. Reading the change event back would have worked too, but this app's existing convention for anything React-Flow-owned that needs to persist through this graph's frequent `nodes` rebuilds is to track it explicitly in app state and feed it back in (`frameDrag`, `sceneDrag`, `measuredSizeRef` all do this) — matching that convention keeps the mental model of "how does per-node state work in this file" consistent, rather than introducing a second, different mechanism (reading occurrence-based `NodeChange` events) that only Frame selection would use.

Design choice (v0.15.0): selection is now applied by reading back React Flow's own `select`-type `NodeChange` events, rather than extending `selectedFrameId`'s original approach (an app-owned boolean set directly by this app's click/drag-start/pane-click handlers) to also cover scenes and multi-selection. The v0.14.2 architecture note reasoned that matching this app's existing convention (explicit app state, fed back in) mattered more than which specific mechanism populated that state — that's still true here, `selectedGraphIds` is still explicit app state fed back in every recompute, exactly like `frameDrag`/`sceneDrag`/`measuredSizeRef`. What changed is *what populates it*: hand-rolling click/Ctrl-click/box-select/pane-click/Escape logic to match React Flow's own semantics would mean re-implementing behavior the library already correctly implements internally and already reports through `onNodesChange` — the same channel this app already listens on for `dimensions` changes. Once multi-selection (Ctrl+click, box-select) was actually in scope for this sprint (unlike v0.14.2, which only needed one frame selected at a time), reading the change events became clearly simpler than reimplementing their logic, not just equally valid.

Design choice (v0.15.0): `multiSelectionKeyCode` was left at React Flow's OS-aware default (`Control` on Windows/Linux, `Meta` on macOS) rather than hardcoded to `"Control"` to literally match the request's wording ("Ctrl + Left Click"). The request's author works on Windows, where the default already produces exactly that behavior — hardcoding it would only diverge from the request on a platform nobody asked about (macOS), trading a real convention (Cmd+click) for no actual benefit today.

Design choice (v0.15.0): a Frame's live-resize overlay (`frameResize`) is threaded into `FrameNode` via two callbacks on `data` (`onResize`/`onResizeEnd`), rather than moving `updateFrameRect` itself into the Zustand store as some kind of "live" transient field, or trying to read the resize's `dimensions`/`position` `NodeChange` events generically the way selection now is. Two reasons this is different from the selection choice above: first, `NodeResizer`'s own `onResize` prop already reports exactly the values needed (`x`, `y`, `width`, `height`) with no ambiguity to resolve, so there's no equivalent "reimplementing library logic" cost to reading the generic change events instead — the callback is simply less code. Second, and more importantly, the live overlay state (`frameResize`) has to live in `FlowPanel`, not in the Zustand store or in `FrameNode` itself, for the same reason `frameDrag`/`sceneDrag` always have: it's transient, per-render UI state that would cause unnecessary store-wide re-renders and would need explicit cleanup logic if it lived in the persisted project store instead.

Design choice (v0.15.1): the multi-selection drag fix generalizes `frameDrag`/`sceneDrag` from a single offset into `Map<nodeId, DragOffset>`, rather than switching to reading position-type `NodeChange` events generically the way `selectedGraphIds` reads selection events. React Flow's own change-event stream for position updates during a drag is keyed to internal store reconciliation, not to this app's own drag-start "who is the origin position for each of these nodes" bookkeeping (needed to compute a clean `dx`/`dy` per node, not just a raw absolute position) — the existing `{origin, dx, dy}` shape already solves that, so it only needed to become per-id, not replaced by a different mechanism entirely. This mirrors the `frameResize` reasoning above (v0.15.0): read the generic event stream when it removes real reimplementation cost (selection), keep the app-owned overlay shape when the existing one already fits and the library's generic events don't obviously simplify anything (dragging, resizing).

Design choice (v0.15.1): the settle-transition and the group-selection-box fixes were both done as narrowly-targeted CSS additions (a second `:not()` class exclusion; a `background`/`border` override on one selector) rather than broader changes to how `FlowPanel` manages interaction state. Both bugs were purely visual — the underlying mechanisms (`frameResize`, `selectedGraphIds`) were already correct — so the smallest fix that addresses the actual visual symptom is a CSS rule, not a new state variable or a change to how either mechanism populates itself. This follows the same "smallest change that fixes the actual mechanism" principle v0.14.1's design choice already established for the edge-routing fix.

Design choice (v0.16.0): Auto Layout collapses a Frame's contained scenes into that Frame's own dagre node rather than laying every scene out independently and then trying to keep a Frame's boundary wrapped around wherever its scenes end up. Independent per-scene layout would scatter a Frame's scenes across whatever ranks/lanes dagre assigns them individually — destroying the writer's own internal arrangement, which is exactly what the user's "does not affect other behaviours" constraint ruled out. Collapsing to one node per Frame is also what makes the fix a genuinely small, additive change rather than a new layout mode: `computeAutoLayout` itself didn't need to learn anything about Frames at all — it just lays out whatever ids and sizes it's given, same as always — all of the Frame-awareness lives in how `projectStore.autoLayoutScenes` builds that node/edge list before calling it, and in how it applies the delta-shift afterward.

Design choice (v0.16.0): empty Frames (no contained scenes) are excluded from Auto Layout entirely, rather than given a default/minimum size and laid out anyway. An empty Frame has nothing inside it whose arrangement Auto Layout is meant to organize — including it would only move an empty box for a reason the user has no way to see or reason about, which is a worse outcome than simply leaving it exactly where it was. This mirrors the same restraint already established elsewhere in this doc (v0.12.0's `--success`/`.font-technical` left unused rather than retrofitted onto something that didn't need it): don't stretch a feature to cover a case it wasn't asked to handle just because the code technically could.

Design choice (v0.17.0): the pane's cursor override targets `crosshair` specifically, not a return to the browser default (`auto`) or React Flow's own `default`. The brief for this sprint was to improve clarity without adding *unnecessary* cursor changes — reverting to a plain arrow would fix the "misleadingly clickable" problem too, but would communicate nothing about what a left-drag on empty canvas actually does (draw a selection rectangle). `crosshair` is the established convention for exactly that gesture in other creative/design tools, so it replaces a wrong signal with a correct, specific one rather than with no signal at all.

Design choice (v0.17.0): the drag-lift/selection-ring transition widened from `transition-colors` to a full `transition` rather than listing out every specific property (`transition-transform transition-colors transition-shadow` or an explicit `transition: transform, border-color, background-color, box-shadow`). The card's visual states already span multiple CSS properties changing together (border colour, background, transform, box-shadow via Tailwind's `ring-*` utilities) and are likely to gain more as this element's states get refined further — a full `transition` (still scoped to the 150ms duration this app already uses elsewhere for settle animations) covers all of them uniformly without needing to be revisited every time a new property is added to one of the card's conditional classes.

Design choice (v0.17.0): `autoPanOnNodeDrag`/`autoPanSpeed` were declared explicitly even though evaluation confirmed they were already working as React Flow's own defaults — not left implicit just because nothing was broken. This matches the standing practice this codebase already follows for other load-bearing library defaults (see the `edgesFocusable={false}`/`edgesReconnectable={false}`/`deleteKeyCode={null}` props already declared to enforce the graph's non-destructive design, and `multiSelectionKeyCode`'s deliberate "left at default, not omitted" reasoning in v0.15.0): a default this app's own feel depends on is worth pinning in code, so a future library upgrade changing that default can't silently change how this app behaves without a diff calling attention to it.

Design choice (v0.18.0): the native application menu is removed entirely (`null`) on Windows/Linux rather than rebuilt as a trimmed Scriare-branded menu the way macOS gets one. macOS structurally requires *some* menu bar content (it's a permanent OS fixture, and losing Cmd+C/V/X/A and Services integration would be a real regression, not just a cosmetic one) — Windows/Linux have neither constraint: `autoHideMenuBar` already keeps the bar out of sight by default, and Chromium's native text-input copy/paste doesn't route through an application menu on those platforms the way macOS's Edit-menu role matters. Building a trimmed menu there anyway would add a maintenance surface (icons, labels, keyboard-accelerator conflicts with this app's own shortcuts) for a menu bar most users on those platforms will never intentionally open — matching this sprint's own "avoid unnecessary visual effects" instruction more literally than "give every platform an equally-featured native menu" would.

Design choice (v0.18.0): the window's `backgroundColor` fix corrects the *value* (matching the current Dark theme's real `--bg`) without attempting the larger fix of making it theme-aware. The sprint brief's own framing — "if certain items should be completed during packaging or release preparation, explain why" — applies here by the same logic used for the Task Manager process name: a genuinely theme-aware background needs the main process to know the renderer's persisted theme choice before the window is even created, which is an IPC/architecture change, not a constant correction. Shipping a half-measure (e.g. reading `localStorage` synchronously from the main process, which Electron doesn't support across that boundary) would be exactly the kind of "temporary workaround" the brief explicitly said to avoid; naming the real fix as a future opportunity is the more honest option than faking one now.

Design choice (v0.18.0): the Story Graph's visible label changed from "Flow" to "Story Graph," but its internal `flow`/`FlowPanel` identifiers, its `data` shape, and its `scriare:panelCollapsed` storage key were all deliberately left alone. The Sprint 8C brief's own instruction — "improve consistency instead of redesigning" — is exactly the reasoning `FrameNode`'s hover-cursor fix (v0.14.0) and the `--danger` migrations already established in this doc: the bug here is purely in what the *user* reads, so the fix is scoped to exactly that surface. Renaming the internal identifiers too would touch every file in "Folder structure" that references `FlowPanel`/`flow` (a wide, purely-cosmetic-motivated diff) and would silently change the `localStorage` key an existing user's saved layout preference depends on, for zero user-visible benefit beyond code-reads-nicer — a trade this sprint's own scope didn't ask for.

Design choice (v0.19.0): `NewProjectDialog.tsx` was rebuilt on `<Modal/>` rather than patching its hand-rolled backdrop/keydown handling piecemeal (adding just a blur class, or just an Escape listener, to its existing structure). A dialog that duplicates the shared shell's behavior slightly differently is exactly the kind of gap this sprint's evaluation was designed to find (see the new pitfall entry in "Known pitfalls") — patching the symptom would leave the duplication itself in place, still one Escape-handling/backdrop-styling change away from drifting out of sync again the next time `Modal.tsx` itself is touched. Reusing the actual shared component, the same fix already applied to every other dialog in the app, is the smaller and more durable change, matching this doc's standing "smallest change that fixes the actual mechanism" principle (v0.14.1, v0.15.1) — here, the actual mechanism is "which component owns dialog chrome," not "which specific CSS classes are missing."

Design choice (v0.19.0): of sixteen systems evaluated this sprint, fifteen were left untouched, and that ratio was treated as the correct outcome rather than a sign the evaluation wasn't thorough enough. The brief's own instruction — "if something already feels production-ready, leave it unchanged" / "do not polish for the sake of polishing" — is the same restraint this doc has already exercised at each of the last several evaluation sprints (v0.14.0's Story Graph pass left node dragging and zoom/pan untouched; v0.17.0 left node dragging, zoom/pan, and edge-path rendering untouched a second time; v0.18.0 left the window title, window icon, and most of the app's spacing/typography untouched): a sprint whose mandate is "evaluate before changing" is doing its job precisely when most evaluated systems come back "already correct," and inventing a change to justify the evaluation would be the actual failure mode here, not finding few gaps.

Design choice (v0.8.1): `setStartScene` takes `string | null` rather than gaining a separate `clearStartScene()` action. A single action with a nullable parameter keeps "set" and "unset" as one code path (one place that writes `startSceneId`, one place every UI calls into) instead of two actions that could drift — the same reasoning behind keeping `startSceneId` a single field in the first place (see "Known pitfalls").

Design choice (v0.8.0): the runtime's extensibility point (`RUNTIME_BLOCKS` in `runtime/registry.ts`) is deliberately a separate registry from the authoring-side `NARRATIVE_BLOCKS`, rather than one combined list. A block's *authoring* behavior (what the slash menu inserts) and its *playback* behavior (how it renders during Play) are different concerns that don't always change together — Divider and Quote need no playback registry entry at all (they're just static HTML via `generateHTML()`), while Choice needs both. Keeping them separate means a future block can register only the side it actually needs.

Design choice (v0.7.0): a `choiceBlock` node's attrs are `{blockId: string, options: ChoiceOption[]}` rather than going back to a `Scene`-level array. Grouping multiple options under one block (instead of one block per option, which is what v0.4.0–v0.6.x did) is what lets "add another path" be an action *inside* the existing block — consistent with the milestone's core rule that narrative elements embed into the document rather than multiplying separate elements for what is conceptually one decision point.

Design choice (v0.5.0): the Content Browser's tree is a separate concern from `Scene.frameId`/`Scene.position` (which are purely for the graph's visual grouping) and from `Scene.choices`/content (the story's branching). A scene's place in the Content Browser lives entirely in its `ContentLeaf` (`parentId`/`order`), not duplicated onto the Scene itself — one source of truth per relationship, matching how Frame membership already works.

Design choice (v0.4.0): choices moved from a separate `Scene.choices` array into the document itself, as atomic `choiceBlock` Tiptap nodes. The `Choice` type didn't disappear — it's still the shape everything outside the editor works with (the graph, Play Mode's "has any linked choice" check, the Inspector's read-only summary) — it's just derived on demand from the document via `extractChoices()` instead of being a separately-maintained array that could drift out of sync with what's actually written. This is why the projectStore has no `addChoice`/`updateChoiceText`/`removeChoice`/`setChoiceTarget` actions: editing a Choice Block's attrs goes through Tiptap's own transaction system, which already flows into `updateSceneContent` via the editor's `onUpdate`.

Design choice (from v0.2.0): Scene and Frame positions are both always **absolute** — a scene's position is never expressed "relative to its frame" (unlike React Flow's native parentId/child-node feature). This keeps every other consumer of `scene.position` simple (dagre layout, containment checks, JSON serialization) at the cost of the graph itself doing a bit more work: frame-drag "moves children" is implemented as a local, non-persisted drag-offset in `FlowPanel` (applied only to the rendered node positions while dragging) that gets committed to the store — shifting the frame and every scene with a matching `frameId` by the same delta — only on drag-stop. Frame membership (`Scene.frameId`) is auto-assigned/cleared on scene drag-stop by checking whether the scene's center point falls inside a frame's rectangle (Figma-style), not by any explicit "add to frame" UI action; as of v0.10.0 that same check (`findContainingFrame()`) also drives the live drop-target highlight while dragging, not just the eventual commit. As of v0.10.2, scene dragging is tracked with the exact same kind of local, non-persisted drag-offset state (`sceneDrag`) that frame dragging always used — see "Known pitfalls" for why that offset isn't just a nice-to-have for scenes, but the only thing that makes them visually move at all in this app. As of v0.10.3, that offset's own downstream cost is kept separate from content-derived graph data (edges, choice counts) for the performance reason also covered in "Known pitfalls." As of v0.10.4, every node object built from these offsets also carries forward a cached `measured` size (`measuredSizeRef`, fed by a newly-added `onNodesChange` handler) so that rebuilding a fresh node object every drag frame no longer resets React Flow's own internal size tracking for that node — see "Known pitfalls" for the freeze bug this fixes. As of v0.10.6, a `measuredVersion` state counter — bumped on a real cache change AND correctly listed in the `nodes` memo's own dependency array (v0.10.5 shipped the bump without the dependency-array wiring, so it had no observable effect) — makes the MiniMap and anything else reading the `nodes` array reflect a node's real size immediately, on first launch and after every Flow-panel collapse/reopen, rather than only after the next drag. As of v0.14.2, `selectedFrameId` joined this same family of explicitly-tracked, explicitly-fed-back-in per-node state, for the same underlying reason (React Flow's own internal state doesn't survive this app's frequent `nodes` rebuilds); as of v0.15.0 it was generalized into `selectedGraphIds` (covering scenes too, and populated from React Flow's own `select`-type change events rather than bespoke click handlers) and joined by a `frameResize` overlay for live Frame resizing — see "Known pitfalls." As of v0.15.1, `frameDrag`/`sceneDrag` themselves became `Map<nodeId, DragOffset>` rather than a single dragged id, so this same family of state now also correctly covers a multi-node selection dragged as one group, not just one dragged frame or scene at a time. As of v0.16.0, Auto Layout writes into these same absolute `position` fields via a delta-shift applied to a Frame's contained scenes, rather than repositioning each one independently — see "Auto Layout and Frames architecture."

Play Mode adds no new fields to the data model at all beyond `startSceneId` (which already existed) — `isPlaying`/`playSceneId` live only in the Zustand store's runtime state, never serialized to the project JSON, since playing is a pure presentation over existing scenes/choices. Likewise the editor/graph split height (`EditorGraphSplit`), the Content Browser's tree expand/collapse state, and (as of v0.11.0) which panels are docked away are all personal layout preferences kept in `localStorage`, never written into the project file. The v0.6.0 multi-selection state (`selectedIds`, `selectionAnchor`) is local React state in `ContentBrowser.tsx` — even more ephemeral than a layout preference, and never persisted anywhere.

Recent projects are tracked separately (not inside any project file) as `recent-projects.json` in Electron's userData folder.

- **v0.17.0**: Story Graph Interaction Feel (Sprint 8B) — a third explicit "evaluate before changing" pass on the feature-complete Story Graph, this time scoped to *feel* rather than mechanics: cursor states, drag feel, hover feedback, selection feedback, navigation feel, edge behaviour, auto-scroll, and cross-interaction consistency, evaluated category by category with instructions to change only what genuinely fell short. Polished: the scene card's drag-lift/selection-ring transition (previously `transition-colors` only, so the scale and ring snapped instead of easing) widened to a full `transition`; the pane's permanently-active `pointer` cursor over empty canvas (a React Flow default this app's always-on `selectionOnDrag` triggers unconditionally, not just during an actual selection drag) replaced with `crosshair`, the conventional drag-to-select cursor. Implemented because missing: hover feedback on a Frame's `NodeResizer` handles (previously none at all); edge highlighting broadened to also react to `selectedGraphIds` (a scene picked up via Ctrl+click/box-select), not just the one scene open in the Scene Editor. Corrected for consistency: the Auto Layout button's tooltip, still describing its pre-v0.16.0 behavior; a mismatched 300ms/400ms camera-fit duration between the initial mount and Auto Layout's own post-layout fit, unified under one `CAMERA_FIT_DURATION_MS` constant. Confirmed already correct and left untouched: node dragging/drop predictability, zoom/pan/large-graph movement, edge-path rendering continuity, and auto-scroll while dragging near the viewport edge — the last of these traced through React Flow's own source (`XYDrag`'s `autoPan()`) and confirmed already working via the library's own defaults, which are now declared explicitly in code rather than left implicit. See "Graph interaction architecture," "Design choice (v0.17.0)," and "Known pitfalls."
- **v0.18.0**: Desktop Identity & Workspace Polish (Sprint 8C) — the evaluation lens widened for the first time from the Story Graph specifically to the application as a whole, again strictly "evaluate before changing," not a redesign. Native desktop identity: `main/index.ts` now calls `app.setName("Scriare")` (`package.json`'s lowercase "scriare" no longer leaks into `app.getName()`-reading native surfaces), `app.setAppUserModelId(...)` (Windows taskbar identity), and `app.setAboutPanelOptions(...)` (a real Scriare About panel instead of Electron's generic default); most significantly, this app's first-ever `Menu.setApplicationMenu()` call replaces Electron's own default application menu — which showed literally "Electron" on macOS and linked to Electron's own site/docs/Discord in Help on every platform — with a minimal three-role macOS menu (App/Edit/Window) and no menu at all on Windows/Linux. The window's background-flash colour, stale since v0.12.0's Minimal redesign replaced the palette it was tuned for, was corrected to the Dark theme's real `--bg` via an OKLab→sRGB conversion. Workspace/panel/desktop-UX consistency was evaluated category by category (spacing/padding/typography hierarchy, panel resize/collapse/focus behaviour, a simulated full writing workflow, keyboard/cursor/context-menu consistency) and found already solid throughout — nothing there needed changing. Visual consistency turned up two more hardcoded-red-instead-of-`--danger` spots the v0.12.0/v0.14.0 migrations had missed (`ChoiceBlockView.tsx`'s two remove buttons, `ContentContextMenu.tsx`'s destructive-item text), both fixed, plus one naming inconsistency (the Story Graph panel's visible label read "Flow," a leftover technical name, while every other reference to it — Content, Scene Details, this doc — already says "Story Graph"; only the visible label text changed, not the internal `flow`/`FlowPanel` identifiers or storage key). Deliberately deferred, and named as such rather than half-fixed: real OS-level packaging (Task Manager process name, executable metadata — this project has no `electron-builder` setup at all yet, making this a build-pipeline undertaking, not a code tweak) and a fully theme-aware window background (would need a main-process-readable persisted theme choice via IPC, not just a corrected constant). See "Desktop Identity architecture," "Design choice (v0.18.0)," and "Known pitfalls."
- **v0.19.0**: Existing Features Evaluation & Final Polish (Sprint 8D) — the final pass of the Sprint 8 arc, widening the evaluation lens once more from the desktop shell (Sprint 8C) to every existing feature in the app: the rich text editor and toolbar, Choice Block, the Content Browser, the Story Graph, Scene Details/Inspector, Project Settings, Play Mode, Dialogs, Popups, Context Menus, Keyboard Shortcuts, Drag & Drop, Folder/Scene Management, and the Start Scene workflow, plus a simulated end-to-end writing workflow to surface friction a category read alone wouldn't catch. Of sixteen systems evaluated, fifteen were already production-ready and left untouched. The one genuine gap: `NewProjectDialog.tsx` — the very first dialog any new user sees — was the sole dialog in the app never migrated onto the shared `<Modal/>` shell, so it alone had a hardcoded, non-token backdrop colour with no blur and no reliable Escape/click-outside dismissal (it only appeared to close on Escape because its text input still had DOM focus); rebuilt on `<Modal/>` to match every sibling dialog exactly. Technical debt identified but deliberately left for a future sprint, per the "don't polish for the sake of polishing" instruction: `EditorToolbar.tsx`'s literal-amber highlight-tool icon, the native colour-swatch inputs' raw hex values (correct as-is — writer content colour, not app chrome), `EditorGraphSplit.tsx`/`ContentBrowser.tsx`'s separate localStorage try/catch patterns, and `TopBar.tsx`'s still-disabled Export button. See "Existing Features Evaluation & Final Polish architecture," "Design choice (v0.19.0)," and "Known pitfalls."
